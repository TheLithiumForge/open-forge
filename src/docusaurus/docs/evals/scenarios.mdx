The evals run as scenarios. Each one answers one question and adds one mechanism, and it starts only after the one before it has been checked. For now each cell runs once, so the numbers are a first read, not a measured difference. Layer 4, the existing app, runs first because it takes the least time and gives the most meaningful results. Layer 3, the full spec, follows. Layers 2 and 1 keep their earlier runs as their baseline.

## Context steps

Each step adds one thing to the step before it, so each comparison has one cause.

| Step | Setup | What the agent gets |
| --- | --- | --- |
| 1 | Code only | The project, its tests and the request |
| 2 | Plain docs | The same, plus the spec documents, with every word but no links between them |
| 3 | Organized docs | The same documents with their links, as a careful team keeps them. This is the control. |
| 4 | Full Core | Open Forge with the spec moved in unchanged and indexed, with every document loaded up front |
| 5 | Full Core, scoped | Open Forge with the spec routed by scope, so a task loads only the parts it needs |

Code only takes information away, and Plain docs takes the organization away, so both compare with Organized docs. [Setups](setups.mdx) defines each setup.

Two variants add the notes a real project collects beside its spec: decisions, analyses, ideas that were rejected or parked, and tryouts and spikes. The notes add no requirement, so any change they cause is noise.

| Variant of | Setup | What the agent gets |
| --- | --- | --- |
| 3 | Overloaded docs | Organized docs with the notes mixed into `docs/` |
| 5 | Full Core, scoped, with memory | Full Core, scoped with the same notes on Memory routes, decisions as accepted knowledge and the rest as candidates |

Each variant compares with its step, so the pair shows whether Memory routes keep the notes from getting in the way.

## Layer 4

| Scenario | What runs | Steps | Way of working | Runs | Question |
| --- | --- | --- | --- | --- | --- |
| L4-1 | Four small repairs, each in one scope: best score, arrow keys, reduced motion and silence | 1 to 5 and both variants | One agent | 28 | What does each step change on small work, what does scoping save, and what do the notes cost? |
| L4-2 | The same four repairs as a chain, each starting from the previous result | 2 to 5 and both variants | One agent | 18, reusing L4-1 for the first repair | Does scoping keep its saving as changes pile up? |
| L4-3 | All four repairs in one request, worked one at a time with tests after each | 3 and 5 | Sol alone, Sol leading Sol subagents and Sol leading Luna subagents | 6 | What does a team cost against one agent for the same work, does a smaller subagent model save tokens, and does scoping lower the subagents' cost? |

A team is part of the implementer, as a model is. Any scenario can run with any team, and the Results page filters by team the way it filters by model, so teams are a selection of the data, not scenarios of their own.

Each chained repair in L4-2 has a twin in L4-1, the same repair from a clean start. The difference between them shows what the earlier changes did. [Starting points](starting-points.mdx#scoped-tasks) describes the four repairs.

## Measures

Layer 4 scenarios run no model judges. Clause checks grade each repair, and `judge --missing` can still add judgments from the saved files later. The objective measures come from each run's saved logs: tokens in total and per task, tokens by file type and tool calls by kind. They're checked on the four L4-1 smoke runs before the full batch runs. [Measures](measures.mdx) defines the numbers the evals already report.
