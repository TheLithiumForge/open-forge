# Scenarios

A scenario is the project context an agent starts with in an eval run, from an empty folder to a full Open Forge install. Plan files and records call a scenario a setup, so the published [setup ladder](../demos/index.md#setup-ladder) keeps its meaning.

Within one comparison, every scenario gets the same prompt, the same requirements, the same starting code and the same simulated user. Only the arrangement of the context changes. For example, Organized docs and Essentials both hold the same short brief in `docs/`, and Essentials also routes it through the Open Forge loader.

Six setups are rungs 0 to 5 of the [setup ladder](../demos/index.md#setup-ladder), the scale the Demos use for how much setup a project has. Spec in prompt, Code only and Plain docs are delivery variants. They move or remove the documents instead of adding setup. Full Core, scoped keeps Full Core's install and routes the documents by scope. Overloaded docs and Full Core, scoped, with memory add the notes a real project collects beside its spec, so they test whether an agent can tell the spec from the history around it.

## Control

Each comparison measures every scenario against a control, the first setup in its plan. The control is No setup for an idea, and Organized docs for a short brief, a full spec and an existing app. [Starting points](starting-points.mdx#compared-setups) lists the setups each starting point compares, and [Results](results.mdx) shows each setup's difference from its control.

## How scenarios are built

The runner builds every scenario from one source, so scenarios differ only where their definitions say. Each project starts in a fresh folder outside any Git repository, so no parent `AGENTS.md` or `CLAUDE.md` reaches the agent. Setup manifests and grading files stay outside the project.

The Open Forge setups use the pinned Open Forge CLI. For an idea, the runner runs one install command, e.g. for Essentials:

```sh
open-forge install --preset essentials --automatic
```

From a short brief on, the documents are written to `docs/` with a description and tags in their frontmatter. Then the runner installs the preset and routes the documents:

```sh
open-forge install --preset essentials --frontmatter scoped --automatic
open-forge route include ./docs --tag LoadNow
open-forge index ./docs/_docs.md
```

Full Core, scoped moves the documents into their scope folders and writes each scope's entrypoint with its description before these commands run. `index` gives a new entrypoint a placeholder description for its author to replace, so the runner writes the real one first, as an author would. Only the overview keeps its `LoadNow` tag. The scope layout is `src/evals/benchmarks/neon-pairs/scopes.json`.

Each command runs with `--dry-run` first, and the setup stops if any command doesn't complete. Before the scored runs, the [`qualify`](cli.md#qualify) command installs fresh setups and checks their entry files, the Open Forge lock file, the planned files and any unwanted files.
