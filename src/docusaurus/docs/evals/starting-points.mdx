# Starting points

A starting point is how much an eval tells the agent about the task before it starts, from a one-line idea to an existing app it has to change.

Every starting point builds or changes Neon Pairs, a browser memory game where you reveal two cards at a time to find the matching pairs. Each one gives the agent more to work from and checks more of the result. For example, an idea leaves the mismatch delay to the agent. A short brief states that a miss closes after 800 active milliseconds, and a check tests it.

Plan files and the CLI number the starting points as layers 1 to 4, in the order below. The [Greenfield demo](../demos/greenfield.md) and the [Brownfield demo](../demos/brownfield.md) show where each input lives and how to try it with your own agent.

### Bug fixes \{#scoped-tasks}

B1 to B4 are small bug fixes to the existing app that each need one scope of the spec, the way most work on a real product does. They test the promise behind [Full Core, scoped](scenarios.mdx#full-core-scoped): an agent that reads only the scope a task needs should spend fewer tokens than one that loads the whole spec up front, and get the same result.

Each task's checks are the full spec's own checks for the clauses it repairs. Every other full-spec check runs as a regression check, so a fix that breaks something else fails.

## Compared scenarios \{#compared-setups}

Each starting point compares its own scenarios. The first one in each row is the control:

| Starting point  | Layer | Scenarios compared                                                                                                                                    |
| --------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| An idea         | 1     | No setup, Minimal, Essentials, Full Core                                                                                                            |
| A short brief   | 2     | Organized docs, Plain docs, Linked AGENTS.md, Minimal, Essentials, Full Core, Spec in prompt                                                        |
| A full spec     | 3     | Organized docs, Plain docs, Linked AGENTS.md, Minimal, Essentials, Full Core, Full Core, scoped                                                     |
| An existing app | 4     | Organized docs, Plain docs, Overloaded docs, Linked AGENTS.md, Minimal, Essentials, Full Core, Full Core, scoped, Full Core, scoped, with memory, Code only |
| P1 and B1 to B4 | 4     | Organized docs, Code only, Plain docs, Overloaded docs, Full Core, Full Core, scoped, Full Core, scoped, with memory                                |

The full plans in `src/evals/experiments/` run each scenario once for now, and each task or packet counts as its own comparison. [Scenarios](scenarios.mdx) defines every scenario, and [Work](work.mdx) the tasks, packets and work modes.

## Simulated user

The simulated user is a model that answers the agent's questions during a run, from the starting point's frozen answer bank. It runs in its own container, apart from the agent.

A fixed classifier splits each message into separate questions and matches each one to a topic in the bank:

- A question with a matching topic gets the bank's answer, word for word.
- Any other question gets "Your call, within the supplied requirements."

The simulated user gives no coding advice and volunteers nothing. The agent gets three rounds of answers. A question after the third round gets the fallback reply, and the run stops after the agent's next reply. Every saved plan uses Claude Sonnet at medium effort as the simulated user for now.
