# Known issues
This page records current verification gaps and operational limits in Neon Pairs.

Verification gaps include test-input dependencies, browser coverage and manual acceptance. The README records a successful result for its named tool combination.

## Reviewed JSON fixtures are required for the complete suite

Status: test-input dependency. The complete unit and browser suites require reviewed JSON fixtures.

Nine JSON files are read by current tests or test helpers. They include package expectations, replay messages, card and face expectations, rejection-sampling vectors, session feedback and browser journey expectations. [Fixtures guide](fixtures-guide.md) gives their exact paths and consumers.

For example, `deck-rejection.test.ts` reads `src/game/deck-rejection.fixture.json` before comparing generated decks. `accessibility-fixture.ts` reads `tests/accessibility.fixture.json` before beginning the tree journey. A file-not-found error at either point says the expected input is missing; it does not prove that the shuffle or accessibility behavior is wrong.

Missing fixtures cannot be recovered faithfully by serializing current production values. Those expectations are intended to provide independent review evidence. Rebuilding them from current output could preserve a defect and make it appear tested. A complete repository copy or the original reviewed inputs is the appropriate source for that evidence.

## Browser artifacts are generated by test runs

Status: generated verification evidence.

The harness writes `test-results/browser-runtime.json`. Individual cases write face-sheet PNGs and the normalized `accessibility-journey.json`.

The test implementation defines the assertions, and the README records the named run. Tree artifacts capture what Chromium exposed during a run. Grayscale sheets capture rendered faces for visual review. These outputs provide the observations behind the verification record.

This is not an application dependency. Opening the built game does not require the test-results directory. Missing results affect confidence and reproducibility of the verification record, not the game's offline asset loading.

## Spoken screen-reader confirmation remains acceptance work

Status: explicitly unconfirmed in the README.

The automated journey inspects Chromium's accessibility tree throughout a complete keyboard game. It checks names, states, result text, completion, native board exit and a new game. The artifact records a null screen-reader field. The README says no screen reader was run.

A tree pass does not establish how a particular assistive-software combination speaks consecutive identical results or queues the final result. The input specification assigns spoken confirmation to user acceptance. [Accessibility audit](accessibility-audit.md) describes the existing evidence and its remaining handoff.

This is an acceptance boundary, not a reason to insert synthetic speech into the game. The game remains silent; assistive software reads the exposed interface. Any future spoken test result would need to identify the actual browser and screen reader used rather than inheriting the current tree-only record.

## Real-device long press is unconfirmed by automation

Status: manual acceptance boundary.

The specification expects the browser's normal context menu and no card activation when that menu opens. The browser suite covers right-click behavior, completed taps, canceled input paths and touch scrolling. It explicitly leaves confirmation of real touch long press to acceptance because automated browsers cannot produce the required native gesture reliably.

A successful touchscreen-emulation tap is not a long-press test. Nor does dispatching a context-menu event prove that a real device presents its native menu. Those observations can help diagnose event handling, but should remain labeled as the narrower checks they are. [Pointer and touch](pointer-and-touch.md) contains the interaction contract.

## Only the recorded Chromium combination has a compatibility result

Status: evidence coverage limit.

The runner imports and launches Chromium. Some tests also use the Chromium DevTools Protocol for accessibility and touch input. There are no Firefox or WebKit projects in this source tree. The README records the named Node/npm/Playwright/Chromium set and says other versions have no test record there.

This does not establish a known Firefox or Safari failure. It establishes that the repository does not supply a result for them. Likewise, mobile emulation does not establish that a physical Android or iOS device was used. [Browser support](browser-support.md) is the compatibility matrix and explains how to read the environment variables and runtime record.

The technology specification permits Node 24.19 or later. That supported floor is separate from a successful run with Node 26.12.1. A command working under another supported Node version needs its own evidence before that version can be described as tested.

## Disk-origin persistence varies by browser

Status: documented platform limit, with a playable fallback.

The delivery path opens `dist/index.html` directly from disk. The technology specification notes that local storage behavior for file URLs differs between browsers and uses a local HTTP origin for persistence checks. The game catches failures when obtaining, reading and writing the store so play can continue in memory.

A user report that a best move record disappears after moving or reopening a disk file may therefore depend on origin behavior rather than the minimum-score comparison. Reproduce saved-preference failures on the HTTP test origin before concluding that the storage adapter violates its contract. Keep a separate report if the game itself stops working when storage is denied; that behavior has explicit regression protection.

The source does not coordinate several simultaneous tabs. The specification leaves multi-tab overwrite behavior outside the tested scope. Active progress is held in memory unless the player exports a snapshot.

## No quantitative responsiveness baseline is recorded

Status: measurement gap.

The repository tests difficult rendering and input paths but records no first-render duration, input-latency distribution or memory ceiling. Assertions have generous automation timeouts to accommodate a busy verifier. Those values do not define acceptable player-visible delay.

The source includes bounded boards, memoized cards, hidden-face omission and an all-inline distribution. These explain expected work and remove some costs, but they do not establish numerical performance. [Performance budget](performance-budget.md) describes useful measurements.

A slow-device report should preserve the action and environment that expose the delay. A deterministic clock test may prove correct elapsed arithmetic while real scrolling still stutters. Conversely, a wall-clock timeout under host contention can fail automation without establishing a product latency regression. The two investigations need different evidence.

For a new defect, the existing board code, snapshot and replay formats can distinguish a deal, a position and timed actions. [Sharing FAQ](sharing-faq.md) explains which to use. [Regression catalogue](regression-catalogue.md) identifies current protections that a report may overlap; excluded behaviors remain defined by the specification.
