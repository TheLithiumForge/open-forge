# ADR 038: Keep play free of analytics

This record explains why the game sends no play telemetry and how engineers investigate problems locally.

## Decision

The playable game contains no analytics service, tracking request or account integration. It does not report reveals, board codes, durations or completions to a host. This is consistent with the single-file offline delivery model and with the absence of a gameplay backend.

The choice was made because the required game experience did not need aggregate observation. Adding telemetry would introduce network behavior, configuration and data questions that were unrelated to matching a pair. A local game should not depend on contacting an analytics endpoint to perform or finish an action.

## Observability without collection

Engineering still needs ways to understand a failure. Board codes identify initial arrangements, snapshots describe progress and replay files describe timed actions. A person can deliberately include those in a report. Browser tests can also save screenshots, tree records and runtime versions under `test-results`.

Those artifacts are generated by verification tools or explicit user action. They are not background reporting by the distributed page. The distinction is visible in the source layout: test artifact writing uses Node APIs in test files, while the production entry imports game components and browser adapters. [ADR 051](adr-051-test-artifacts.md) explains the evidence outputs.

## Why reproducibility helps

A deterministic deal turns a vague report into a concrete starting point. A replay can isolate the exact ordering of a mismatch timeout and another activation without asking a remote logging service what happened. The pure core makes this route practical because it can execute outside the browser with the same rules.

This is especially useful for a game that can be opened from disk. A report need not come from a stable hosted origin, and the developer does not need access to a user's local storage. The person reporting the issue can choose what to export and share. [Sharing FAQ](sharing-faq.md) explains which format answers which question.

## Alternatives and costs

A small anonymous event counter would still be a runtime request and a service dependency. Detailed session traces could make some investigations easier but would require a policy for collection and retention that the current product does not need. An opt-in diagnostics upload would be another feature with its own UI and server path, rather than a free addition to an existing local tool.

The cost is less knowledge about real-world aggregate use. The project cannot infer common board choices or completion rates from a service it does not run. Playtest notes can inform design, and explicit reports can explain individual issues, but those are different evidence sources from passive production telemetry.

## Source and artifact checks

The source audit rejects request APIs in shipped authored code, and the built-output check looks for unwanted fetch and module-preload code. Browser delivery tests block requests when opening the final file. These checks support the broader offline contract; they also make accidental telemetry integration visible.

A grep for a vendor name alone would not establish the absence of networking. A generic request helper or an injected build helper could make requests without using an analytics label. Inspecting source boundaries and the actual artifact gives a more useful combination of evidence.

[ADR 004](adr-004-no-backend.md), [ADR 027](adr-027-offline-first.md) and [Offline delivery](offline-delivery.md) explain the related architecture. This record is about the deliberate absence of play collection, not a claim that the development tools never use a network during installation or browser downloads.

## The production composition imports

The browser entry composes game behavior directly. Diagnostic artifact writers and server setup belong to the separate test environment, not this component tree.
