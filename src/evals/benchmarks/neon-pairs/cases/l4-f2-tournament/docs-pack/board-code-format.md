# Board code format
This page documents the version 1 board-code string, its parser and the deterministic deal generated by `src/game/deck.ts`.

A board code is the smallest reproducible game artifact. It identifies a starting arrangement, independent of moves, matched cards and elapsed time. Use it to repeat a deal with Restart, share a starting board with another player, or give a test a deterministic deck. Use a [snapshot](snapshot-format.md) when the position itself matters and a [replay](replay-format.md) when action order matters.

## The string and its domain

The version 1 form is `np1-N-seed`. `N` is one of `4`, `6`, `8`, `10`, `12`, `14` or `16`. The seed is a decimal integer from `1` through `2147483646`, inclusive. The letters and punctuation are literal. Neither numeric component uses leading zeros, signs, spaces, exponent notation or decimal points.

`np1-4-1` is the published example: version 1 generation, four rows and four columns, seed 1. `np1-16-2147483646` uses the largest supported board and largest accepted seed. Both code components are needed; the seed alone does not determine deck length or the resulting sequence of swaps.

| Code | Parser result | Reason |
| --- | --- | --- |
| `np1-4-1` | `{size: 4, seed: 1}` | Supported size and positive seed |
| `np1-6-2147483646` | `{size: 6, seed: 2147483646}` | Upper seed endpoint is included |
| `np1-04-1` | `null` | Leading zero in size |
| `np1-4-01` | `null` | Leading zero in seed |
| `np1-5-1` | `null` | Well-shaped number, unsupported side length |
| `np1-4-0` | `null` | Seed range starts at 1 |
| `np1-4-2147483647` | `null` | Above `SEED_MAX` |
| `np2-4-1` | `null` | Prefix is not the implemented generation version |
| `np1-4-1e2` | `null` | Seed spelling is not decimal digits alone |
| `np1-4-+1` | `null` | Sign is not part of the accepted form |

There is no checksum, title, player name or progress suffix. A typo can produce another valid code, so parser success cannot confirm that the sender intended that particular seed. The code is an identifier of generation inputs, not a signed statement about the game.

## Parser, constructor and generator

`parseBoardCode(code)` returns `{size, seed}` on success and `null` on failure. Its pattern is built from the private `BOARD_VERSION = 'np1'` and the two positive decimal components. After converting those components with `Number`, it verifies `isValidSize(size)`, `Number.isSafeInteger(seed)` and the upper seed limit. Positivity is already constrained by the lexical form.

`boardCode(size, seed)` formats those arguments into a string, calls the parser on the result, and throws `Error('Invalid board code.')` if validation fails. It is a checked constructor, not a formatter that clamps or rounds its arguments. A caller supplying a fractional seed does not obtain a nearby legal seed. `generateBoard(code)` also validates and throws the same error before building a deck.

`isValidSize(value)` checks membership in `GRID_SIZES`; it does not accept every even integer. Keeping the size catalogue explicit matters because generation, artwork and layout are tested against the seven supported sizes. A syntactically plausible code for another size is still invalid.

The `Board` returned by `generateBoard` contains `boardCode`, `size`, `seed` and `deck`. Both the board object and its deck array are frozen. Its interface marks them readonly as well. A `GameState` adds mutable-over-time progress through new returned objects, while keeping the generated board description and deck stable. See [Game state model](game-state-model.md) for that distinction.

The pure parser does not trim a code. The browser's `useGame.loadBoard` trims the Board code draft before calling it. Board codes embedded in snapshot and replay JSON go directly to the parser and therefore need their exact spelling. This explains why a copied code with outer spaces can load through the text control but fail when those spaces are inside the JSON string.

## Position order and pair identity

The initial deck has `N * N` positions, numbered from zero in row order. Before shuffling it is built with `Math.floor(index / 2)`, giving `[0, 0, 1, 1, ...]`. There are `N * N / 2` faces, and every face appears twice. Shuffling swaps positions; it does not change the face values or duplicate counts.

| Side length | Positions | Distinct faces | Largest position index |
| --- | --- | --- | --- |
| 4 | 16 | 8 | 15 |
| 6 | 36 | 18 | 35 |
| 8 | 64 | 32 | 63 |
| 10 | 100 | 50 | 99 |
| 12 | 144 | 72 | 143 |
| 14 | 196 | 98 | 195 |
| 16 | 256 | 128 | 255 |

A numeric face is an identity used to decide matches and choose artwork. A position is an address on this particular board. The distinction continues into the other formats: snapshot `matched` values and replay action `index` values are positions, not faces. Regenerating the deck is what gives those positions their meaning.

Changing SVG artwork without changing face identity does not by itself change this array. Changing the mapping from generated numbers to matching identity would affect gameplay and therefore deserves a generation compatibility review. The string encodes a deal algorithm, not pixel output; [Card artwork](card-artwork.md) covers the rendered faces.

## Park-Miller state sequence

Generation starts a local variable at the parsed seed. Each draw uses `nextRandomState(state)`, defined as `(state * 16807) % 2147483647`. The modulus is `SEED_MAX + 1`. For seed 1, the first five resulting states are:

```text
16807
282475249
1622650073
984943658
1144108930
```

These values are independent of the browser clock, prior games and React rendering. The state variable belongs to this one call to `generateBoard`. Generating a second board starts again from its own seed rather than continuing a global sequence.

The specification calls for exact integer arithmetic. JavaScript's numeric multiplication is exact for the integer products involved here: the maximum relevant product is under `2^53`. A port to a language with narrower integer multiplication needs to preserve the same arithmetic rather than relying on overflowing 32-bit products. The `%` operation is applied to positive values, so signed-remainder differences do not enter a valid generation.

This is a reproducible pseudorandom sequence, not a secret. Knowing the seed is sufficient to calculate it. No security property depends on hiding it. Fresh-deal seed selection is separate browser session behavior; it does not alter the meaning of an existing code. [Deck generation](deck-generation.md) provides gameplay context for the shuffle.

## Bounded draws and why rejection matters

A shuffle needs an integer in a range whose width changes on every iteration. Let `b` be that width and `q = 2147483646`. The implementation calculates `limit = floor(q / b) * b`. It advances the generator, sets `draw = state - 1`, and retries while `draw >= limit`. An accepted draw maps to `draw % b`.

Subtracting one changes the generator's `1..q` state range into `0..q-1`. Keeping only a whole multiple of `b` values gives every remainder the same number of representatives. Directly taking a remainder from all `q` values would slightly favor some outcomes whenever `b` does not divide `q`.

For the first iteration of a 4 by 4 shuffle, `b` is 16. `limit` is `2147483632`, so draws from that value through `2147483645` are retried. Seed 1's first draw is `16806`, which is accepted and maps to `6`. Position 15 swaps with position 6 in the initially paired deck.

The retry consumes another generator state. That consumption is part of the versioned algorithm. A port that uses the right remainder but omits rejection will agree with many ordinary seeds and still diverge for others. Similarly, accepting a draw equal to the limit is wrong: the retry comparison is `>=`, not `>`.

There is no fixed promise that every shuffle iteration consumes exactly one state. There are exactly `N * N - 1` swap iterations, but a rejected draw can make the total state-advance count larger. Recording the number of accepted swaps alone is therefore not enough to reconstruct where a faulty implementation diverged.

## Shuffle order is observable compatibility

`generateBoard` walks backward from the last deck index to index `1`. At index `i`, the bound is `i + 1`; the chosen position is in `0..i`, including `i`. It then exchanges the faces at `i` and the chosen position. Selecting the current index is a legitimate no-op swap and still consumes its accepted draw.

A forward shuffle using the same generator can be unbiased and still produce a different deck. Starting from a different pair ordering can also produce a valid memory game while breaking all existing codes. Version 1 fixes the entire recipe: initial array, generator constants, accepted-draw rule, iteration direction, bounds and swap behavior.

The code includes an explicit guard against an undefined face at either swap position, throwing `Deck index out of range.`. Valid inputs and the bounded draw algorithm keep indices inside the constructed array. The guard is an internal invariant check rather than an alternate parser result. Importers receive a normal generated board once validation succeeds.

## Published deck and an actionable example

For `np1-4-1`, the resulting deck is:

```text
[6, 7, 0, 5, 2, 2, 0, 5, 3, 7, 1, 6, 4, 4, 1, 3]
```

In row order the same data is:

```text
6  7  0  5
2  2  0  5
3  7  1  6
4  4  1  3
```

Positions `2` and `6` contain face zero and form a pair. Positions `0` and `11` contain face six. Positions `0` and `1` have different faces, so activating them produces a mismatch. These examples are useful across formats because they connect a short code to concrete transition outcomes without relying on a hidden-card inspection endpoint.

A minimal browser reproduction can load this code, activate the first two positions, and observe the pending interval. A minimal replay can express those activations at logical time zero. A snapshot can instead directly describe the resulting mismatch with its remaining time. The same board vector makes all three reports comparable.

## Evidence and porting checks

`deck.test.ts` compares the first generator states and example deck with literal values from `game.fixture.ts`. It checks the inclusive maximum seed, complete pair counts, repeatability and frozen output at every supported size. It also compares generation against `tests/deal-oracle.ts`, an independent reading of the algorithm, rather than only calling the production generator twice.

The rejection-focused tests in `deck-rejection.test.ts` cover draws above and exactly at a rejection limit using independent expected decks. That test source loads `deck-rejection.fixture.json`.

For a port, matching the five generator states establishes only the recurrence. Matching the example deck also exercises initial pairing and shuffle order. Comparing several sizes and rejection cases is stronger evidence because a first-deal example may never consume a rejected draw. These layers help localize a disagreement: recurrence, bounded draw, swap ordering or interpretation of position indices.

A changed implementation can be faster or clearer while preserving the same output. Compatibility is judged by the generated arrangement for a valid code, not by the internal loop's spelling. A change that alters arrangements needs a generation-version decision rather than a cosmetic refactor label. See [Format versioning](format-versioning-guide.md) for the relationship between this prefix and the JSON versions that embed it.
