# Fixtures guide
This guide explains the deterministic data, reviewed expectations and browser helpers used by Neon Pairs tests.

The project uses several things called fixtures, with different responsibilities. A TypeScript constant can identify a known deal. A reviewed JSON file can hold independent expected output. A browser helper can load a page and perform actions. A generated PNG or accessibility-tree record is an artifact from a run. Confusing these roles can turn a regression test into a comparison of current code with itself.

## The published deal is the common anchor

`src/game/game.fixture.ts` contains `EXAMPLE_CODE`, `EXAMPLE_DECK`, `EXAMPLE_PAIRS`, `RANDOM_STATES` and `SPEC_VECTOR`. These are test data, not a browser endpoint. The example code is `np1-4-1`; its literal deck is:

```text
[6, 7, 0, 5, 2, 2, 0, 5, 3, 7, 1, 6, 4, 4, 1, 3]
```

The pair list groups positions by face in a convenient completion order:

```text
[2, 6], [10, 14], [4, 5], [8, 15],
[12, 13], [3, 7], [0, 11], [1, 9]
```

Indices are zero-based row-order positions. A first reveal at 2 and second at 6 makes a match. Revealing 0 and 1 makes a miss. These facts let tests choose a transition without reading hidden DOM identity. They also make failures reviewable against the published reproducibility example.

`SPEC_VECTOR` holds literal sizes, format versions, byte/action bounds, mismatch duration and maximum seed. Tests compare production constants with those values. Importing the production constant as the expected value would not provide the same independent check if that constant were changed incorrectly.

`RANDOM_STATES` holds the published initial generator states for seed 1. `deck.test.ts` advances the production generator and compares against the list. The deck vector then checks the shuffle result, so generator correctness and deck ordering are both visible.

## Independent generation covers more than the example

`tests/deal-oracle.ts` implements `specDeal(size, seed)` with BigInt arithmetic. It starts from paired face IDs, advances the specified generator and uses rejection sampling before each descending shuffle swap. It does not call production `generateBoard`.

The deck tests first establish that the independent implementation reproduces the literal example. They then compare production output with the oracle at every supported size. This gives the broader algorithm checks a fixed reference point rather than trusting an independent implementation merely because it is in a test folder.

Rare rejection branches use stored vectors in a separate JSON input. One covers a draw above the limit, and the other covers a draw exactly on it. Those cases exist because ordinary seed-one generation can pass even when a boundary comparison is wrong.

## Reviewed JSON inputs and their consumers

The following paths are all relative to the project root. They are source expectations, not files generated by the documented browser command.

| Expected file | Reader | What the reader compares or validates |
| --- | --- | --- |
| `scripts/package.fixture.json` | `scripts/source-audit.test.ts` | Installed package version expectations |
| `scripts/replay-messages.fixture.json` | `scripts/replay.test.ts` | stderr text for missing, malformed and rule-invalid replay files |
| `src/game/deck-rejection.fixture.json` | `src/game/deck-rejection.test.ts` | Independent complete decks for rejection boundaries |
| `src/game/board/card-state.fixture.json` | `src/game/board/card-state.test.ts` | Three hidden/revealed/matched descriptions |
| `src/game/board/face-design.fixture.json` | `src/game/board/face-design.test.ts` | Designs for face IDs 0, 64 and 9 |
| `src/game/session/session.feedback.fixture.json` | `src/game/session/session.test.ts` | Initial, mismatch, match and win feedback |
| `tests/ui.fixture.json` | `tests/ui-snapshot.ts` | Empty-best, banner, mismatch and winning-result text |
| `tests/accessibility.fixture.json` | `tests/accessibility-fixture.ts` | Complete journey names, results, controls and README record |
| `tests/status-format.fixture.json` | `tests/product-contract.e2e.test.ts` | Initial, matched and imported-completion status text |

The complete suite reads all nine reviewed files. Missing inputs prevent the affected tests from running. [Known issues](known-issues.md) records the impact.

Several readers parse JSON as `unknown` and narrow it. `accessibilityFixture` checks the numeric size, control strings, arrays of strings and several final fields before returning a typed object. `uiSnapshot` checks its four strings. Other tests compare parsed expectations directly with the actual structured value.

The card-state expectation covers hidden position 0, revealed position 6 with face 0 and matched position 15 with face 64. The face-design expectation samples the first solid face, its outlined counterpart and a diagonal-marker face. The all-face table test supplies broader coverage independently of those samples.

## A missing expectation is not an update request

If a test cannot read its JSON input, inspect the path and checkout contents before changing application code. Most paths use `new URL(..., import.meta.url)`, so they resolve beside the reader rather than from the shell's current folder. Changing the working directory will not recover a file absent from that module's directory.

Generating expected JSON from the current production function would make the suite runnable while discarding the review boundary. For example, a bad face label copied from `faceDesign` into its own expectation would pass. Recovering the reviewed input, or independently reviewing any intentional replacement against the specification, preserves the test's purpose.

The project does not expose an automatic “approve all snapshots” command in `package.json`. Its snapshot terminology includes explicit JSON expectations and the product's progress format, not only a testing framework feature. A snapshot test failure can therefore mean several different things; the reader and compared fields identify which one.

## State builders keep invalid cases precise

`snapshot.test.ts` has a local builder that serializes a complete valid initial progress object plus overrides. Later baselines represent started progress with one revealed card or a pending miss. The tests first accept those baselines and then change a counter or selection fact.

That approach avoids invalid-by-default fixtures. A started game with zero moves and a closed selection is already inconsistent. Adding a negative counter to it would not isolate the counter validation. The one-card baseline makes the intended reason for rejection visible.

Completed progress can be constructed from the literal pair positions. Larger completed states use every index, a closed selection, a sufficient move count and a started flag. Browser tests load those through Snapshot JSON when the question concerns presentation of imported completion, rather than spending time playing every large-board pair.

This is different from proving live completion. `completion.test.ts` and the browser play journey activate cards through the relevant action path. An imported completed board cannot establish that the final live turn records feedback, updates preferences or selects celebration correctly.

## Browser helpers act through public controls

`tests/game-fixture.ts` exports disk URLs for the game and both diagnostic entries. It also exports `PHONE`, the 360x800 viewport used by several journeys. The URL constants identify built outputs; the helper does not serve source itself.

`loadFixedBoard` navigates, opens Reproduce a game, fills the known code, loads it, closes the disclosure and checks the card count. Its optional URL argument lets a persistence case use the wrapper's HTTP origin instead of the default disk URL.

`loadTimedBoard` installs the Playwright clock before navigation, loads the same deal and pauses at a controlled later value. The later baseline keeps initialization separate from active play. Individual tests then advance time explicitly and choose when a valid reveal begins counting.

`moves` reads the displayed move value using its status label. `finishBoard` clicks the literal pair positions and checks the matched-card count. `exportedSnapshot` opens the disclosure, uses Export snapshot, parses the textarea, closes the disclosure and checks that the parsed value is an object.

Export is a public action, but it synchronizes active time before returning data. A test that repeatedly exports during an idle hidden interval may alter the observation pattern it is trying to investigate. The idle-clock cases therefore avoid those intermediate observations. [Flaky-test notes](flaky-test-notes.md) explains why that detail matters.

## Diagnostic builds are controlled observation points

The art and session Vite configurations emit separate HTML entries. The sheet captures all faces and compares card styles with the game; the session entry supplies Unmount game for timeout and subscription tracking. Their controls stay outside the distribution. [Browser test guide](browser-test-guide.md) explains loading and instrumenting them.

## Generated artifacts are results, not expectations

The wrapper creates a directory derived from each test's name under `test-results`. `outputPath` accepts a basename. Existing cases write `face-sheet-color.png`, `face-sheet-grayscale.png`, `face-sheet-neutral.png` and the accessibility journey record.

The tree record normalizes browser nodes and excludes environment-specific URLs and internal identifiers. It captures what the current browser exposed during that run, along with tool versions and the explicit absence of a screen-reader run. It is not loaded as the journey's reviewed expected output.

`browser-runtime.json` is another generated result, written by setup rather than by a particular visual case. It identifies the launched tools. A copied runtime record or old screenshot cannot establish that a new candidate passed. The documented command builds from current source to keep that connection understandable.

Keep these distinctions when diagnosing failures: literal vectors establish independent facts, local builders arrange states, helpers drive the interface, reviewed JSON holds expectations, and artifacts describe observations. [Unit test guide](unit-test-guide.md) and [Browser test guide](browser-test-guide.md) show how those parts fit into executable cases.
