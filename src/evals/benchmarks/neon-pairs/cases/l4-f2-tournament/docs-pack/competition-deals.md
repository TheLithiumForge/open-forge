# Competition deals

This page explains deal identity in competition and the existing board-code machinery that can reproduce an arrangement.

The current engine already has a precise way to identify a starting puzzle. A board code describes its generation version, side length and seed. That identity is useful when comparing what people played, investigating an apparent discrepancy or distinguishing a fresh attempt from restored progress.

## Deal identity within an event

A match has a deal identity as well as the identities of its participants. Both players of a match play one board code, and every match in a tournament has a different board code. The identity in that sentence is the complete board code, rather than only the final numeric part or a screenshot of the visible board.

For example, a match associated with `np1-4-73` refers to the arrangement generated by that full string. A later match using `np1-4-74` has a different code. `np1-6-73` is also a different code from the first example: its side length differs even though its seed number is the same. These examples illustrate code identity without introducing a new competition-specific code format.

The distinction between board identity and progress is just as important. A hidden starting board, a board with several pairs exposed and a completed board can all have the same `boardCode`. They are different game states on the same deal. A screen showing more exposed faces does not, by itself, show that a different board was loaded.

## The format already implemented

`src/game/deck.ts` defines the version as `np1`. A code has the form `np1-N-seed`, where `N` is a supported side length and the seed is between 1 and 2147483646 inclusive. The parser accepts decimal notation without leading zeros. It returns the parsed size and seed or `null`.

`boardCode(size, seed)` constructs a string and validates it through `parseBoardCode`, throwing for invalid input. `generateBoard(code)` parses the code, constructs a deck with each face twice and shuffles it. The returned board object and deck array are frozen. There is no participant input in this process.

The exact grammar is in [board code format](board-code-format.md); the fixed generation algorithm is in [deck generation](deck-generation.md). Competition uses this existing deal identity. It does not acquire a new generation algorithm merely because a group is taking part.

The browser entry path has a small distinction from the pure parser. `loadBoard` in `src/game/session/use-game.ts` trims surrounding whitespace before parsing. The parser itself does not perform that trim. This can explain why pasting a code into the UI succeeds while directly passing the same whitespace-bearing string to a core function fails.

## Why a code repeats an arrangement

The deterministic generator begins with the supplied seed. Each state update multiplies by 16807 and takes the remainder modulo 2147483647. The deck starts with consecutive pairs of face numbers, then the shuffle walks backward through its positions and swaps with a selected earlier position or itself.

The bounded draw uses rejection rather than simply applying a remainder to every possible generator output. `SEED_MAX` is the draw range; the accepted interval is the largest multiple of the current bound within that range. A value outside that interval advances the generator again. Those details are part of the existing generation version.

The published example `np1-4-1` produces `[6, 7, 0, 5, 2, 2, 0, 5, 3, 7, 1, 6, 4, 4, 1, 3]`. In that deck, positions 0 and 11 contain face 6. That gives a reviewer a literal check independent of what a screenshot seems to show.

`src/game/deck.test.ts` checks published vectors and each supported size. `tests/deal-oracle.ts` implements an independent reading using BigInt arithmetic. The independent calculation is particularly helpful when an issue concerns an arrangement: calling the production generator twice demonstrates repeatability, but does not alone show agreement with the specification.

## Freshness is narrower in the current session

The ordinary fresh-deal path is `freshBoardCode` in `src/game/session/fresh-board.ts`. It obtains a value from `crypto.getRandomValues`, rejects draws outside its accepted range and converts the result to a valid seed. When supplied a previous seed, it rejects that seed as well.

`newGame` passes the current game's seed to that function. It prevents the immediate replacement from reusing the previous seed, but it supplies no collection of earlier codes. A sequence can therefore revisit an older seed after an intervening game. The helper has no event memory and no match context.

That is the relevant implementation gap for the rule on this page. A large seed range makes a collision unusual in casual play, but probability is not a record of which codes an event has already used. A mockup that repeatedly invokes the existing New Game action has not demonstrated the event-wide property merely because the first few generated strings differ.

The project has no prescribed allocation strategy. Tracking used full codes and considering candidate codes is one possible design direction; preselecting a set is another. Neither approach is implemented in the game.

## Starting state and saved progress

`createGame(code)` produces a game with no matched positions, a closed selection, zero moves, zero elapsed time and `started: false`. The board description and deck come from `generateBoard(code)`. Calling it again with the same code constructs a fresh game over the same arrangement.

`decodeSnapshot`, by contrast, reconstructs the deal and restores validated progress. Its returned state can include matched positions, a revealed card or a pending mismatch. A snapshot carrying the correct code is therefore not automatically evidence that an attempt began from the initial hidden state. [Snapshot format](snapshot-format.md) and [snapshot selection notes](snapshot-selection-notes.md) explain those existing fields.

The same distinction appears in the UI. Restart reconstructs the current code through `createGame`. New Game obtains a fresh candidate first. Load board parses an entered code and starts its initial state. Load snapshot restores progress. These controls share some replacement machinery but do not describe the same operation.

## What reproducibility can establish

A code can establish the arrangement produced by the documented generator. It does not establish who was holding the device, whether someone had watched earlier play or how long the group spent discussing the screen before an attempt. Those are social observations, outside the content of the code.

During an investigation, a full board code is more precise than “the small board” or a seed copied without its size. A snapshot can add the state at the moment of interest. A replay can add timed actions. None of these existing artifacts carries a competition participant model. Their usefulness comes from the game information they actually encode.
