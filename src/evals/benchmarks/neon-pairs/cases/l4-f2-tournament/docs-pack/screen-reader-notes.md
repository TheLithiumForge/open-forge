# Screen reader notes

This page describes the information exposed during a keyboard game and the limits of the project's screen reader evidence.

The interface exposes native controls, card names, state changes and readable results. The repository README records accessibility-tree checks in Chromium 156.0.8078.4 with Playwright 1.64.1. It also explicitly records that no screen reader was run. The names and sentences below are source-backed content available to assistive technology, not a transcript of speech captured in a listening session.

## Finding the game controls

The document language is English, the browser title is Neon Pairs, and the main area contains the game's h1 and introductory text. The first interactive deal control is the native select labeled Grid size. New Game and Restart follow as native buttons.

The select's label is connected with `htmlFor="grid-size"`. Its options read 4x4 through 16x16 at the seven supported sizes. A user can find it by its visible name rather than needing to interpret an unlabeled icon. The action buttons also use visible text as their names.

The statistics are reading content in a definition list: Moves, Pairs, Time and Best. There are no custom accessible labels replacing their values. An absent best is visible as `none`. These details matter when inspecting the tree because the information is ordinary document content, not four editable fields or buttons.

Changing size creates a deal of that size. New Game creates another deal at the current size, and Restart repeats the current code. Those actions retain focus at their controls. They do not suddenly land the player deep in the card board. [Control bar](control-bar.md) describes the callbacks and layout.

## Entering the board

Board's viewport is a region named `Game board` and described by `board-help`. The help text says: `Use a pointer or Tab to enter the board. Arrow keys move between cards. Enter or Space reveals a card.` This is visible text as well as an associated description.

Tab enters at the remembered card. Before any card focus has been remembered, that is the first card. Plain arrows move one row or column with no wrapping. Tab and Shift+Tab can leave the board. Modifier combinations and unlisted keys remain browser input rather than board commands.

The native card button provides activation through Enter and Space. Screen reader interaction modes can affect which keys reach a web page, so a real spoken acceptance journey is still valuable even when the browser's keyboard tests pass. The game's documented input relies on native button activation and board arrow navigation.

Matched cards remain focusable, and navigation does not skip them. During a mismatch or paused import, movement can continue although activating another card has no game effect. This keeps exploration separate from the turn decision. [Board keyboard navigation](board-keyboard-navigation.md) traces the remembered tab stop and target calculation.

## A closed card reveals no hidden identity

`describeCard` builds a one-based coordinate from the zero-based deck index. Index 0 on a four-column board is named `Row 1, column 1, closed`. Index 5 is `Row 2, column 2, closed`. The pattern gives a stable spatial reference before any face is known.

Board passes `face={null}` for a hidden card. Card then renders only the neutral back span with `aria-hidden="true"`, not the Face component. The hidden face is absent from the element's label, attributes and child artwork. A screen reader cannot legitimately read a face description from that hidden DOM because it is not there.

This is stronger than hiding a face SVG with CSS while leaving a revealing title or data attribute. The browser input-contract test compares every hidden card's attributes, inner HTML and text against the expected neutral content. A visual-only inspection could miss such a leak.

The deck still exists in game state because the game must resolve matches. The DOM boundary is the important distinction for the interface: a hidden card control exposes its position and closed state, not its underlying identity. [Card artwork](card-artwork.md) and [Pair identity](pair-identity.md) explain the visual and game sides.

## The first reveal

Use `np1-4-1` as a concrete source-backed example. Its index 0 contains face 6. After activation, that button's name becomes `Row 1, column 1, revealed, cyan solid plus, marker top`. The state precedes the face description in the actual string generated by `card-state.ts`.

Face names come from `faceDesign`: color, solid or outline, shape and marker position. The SVG itself is `aria-hidden="true"` and `focusable="false"`. It does not add a separate graphic description competing with the button name. The name carries the information the player needs to remember.

A first reveal starts elapsed time but leaves Moves at zero. The game has not yet completed a two-card attempt. It also does not publish a turn result merely for that first card. A user can inspect the newly focused control's name, move to another location and make the second choice.

Repeating activation on the same first card does not complete a move. That is an ignored game action, not a second reveal or a reason to read a new turn result. This is useful when interpreting a test that presses Space twice and sees no move increment.

## A match and a miss

On the same example code, index 11 is the partner of index 0. It is row 3, column 4. Activating it completes the pair immediately. Both controls' names use `matched`, retain the face description and expose `aria-disabled="true"`.

The current result text for the first match is `Pair found. 1 pair matched.` Later nonfinal matches substitute the count and plural form. The matched controls remain in the board's spatial navigation even though activating them no longer changes the game. A screen reader may verbalize their unavailable state according to its own conventions; the source exposes the ARIA disabled state.

Indices 0 and 1 are a mismatch on this code. Their faces remain revealed for the active mismatch interval, and the turn result is `No match. Cards close after a short pause.` Additional card activation during that wait is ignored. The interval pauses while the page is hidden or imported progress waits for Resume.

After closure, the two names return to their closed forms and their face artwork is removed. Closure does not publish another turn result. Moving focus while the pair waits also does not republish the mismatch sentence. [Announcements policy](announcements-policy.md) explains the event identity that makes consecutive identical misses distinct without making ordinary renders noisy.

## Completing the game

The winning match produces `Pair found. All pairs found in N moves and time.`, using the final counters. GameStatus also displays the persistent completion sentence `Every pair found in N moves and time. Well played.` A reader can revisit the final statistics and summary in document content.

The time text uses the game's formatter: seconds are padded, and minutes can grow beyond 59. The values stop advancing at completion. The final card remains the active control; completion does not force focus onto the banner.

Matched cards still occupy the board, so Tab leaves it without requiring a pass through every matched position. In the collapsed page layout, the next control is the native reproduction summary. Shift+Tab can return through the remembered board location toward the deal controls. Starting another game resets board memory while leaving the action button focused.

The complete automated journey exercises this path, including a new game after completion. It checks the final summary in the accessibility tree rather than assuming that visible text is necessarily exposed as expected.

## Reproduction tools in reading order

The native summary is named `Reproduce a game`. Expanding it exposes labeled Board code and Snapshot JSON fields with Load board, Export snapshot and Load snapshot actions. The board-code form submits with Enter; the snapshot actions are ordinary buttons rather than an Enter-to-import form.

Invalid input keeps the current game and draft. The visible outcomes are `Invalid board code.` and `Invalid snapshot.`. The load buttons reference the nearby notice paragraph as a description, and the event feedback path publishes the outcome. Clicking a load button leaves focus there. An invalid Enter submission from Board code leaves focus in the input for correction.

A valid unfinished snapshot reports `Loaded snapshot. Select Resume to continue.` and pauses card activation. The player can still explore the board with arrows. Resume focuses the remembered card before the Resume button is removed, then continues active play. A completed snapshot reports `Loaded completed snapshot.`, shows the completed game statically and offers no Resume button.

Export fills readable JSON into the textarea. It does not require clipboard permission or make the text impossible to select. A user can move to the native field and copy its contents through their normal editing commands. [Reproduction panel](reproduction-panel.md) explains draft lifetimes and the different board-code reset behavior.

## What the automated journey records

`tests/accessibility.e2e.test.ts` uses Chromium's debugging protocol to enable accessibility and capture full trees at named stages. Its helper removes ignored nodes and records role, name, scalar value, text and selected accessibility properties. This produces evidence about exposed controls and states without preserving transient browser node identifiers.

The journey finds Grid size and New Game by name, enters the board, inspects closed and revealed names, completes pairs with Enter and Space, checks matched disabled state and reads each turn result. It then checks completion, Tab exit, New Game and repeated load outcomes. The saved artifact is named `accessibility-journey.json` by the test.

The test writes that artifact as output. The source references reviewed fixtures for expected content.

## Spoken acceptance still answers a different question

Tree exposure, keyboard behavior and speech are related but distinct. A browser may expose the correct atomic result while a particular screen reader schedules or phrases it in a way that needs listening review. Consecutive identical misses and the final combined result are especially useful listening points.

The input specification assigns spoken confirmation to user acceptance. The repository README's record says `Screen reader: not run. Spoken journey: user acceptance.` That limitation belongs beside the evidence, not hidden behind a broad statement that screen reader support was tested end to end.

A useful acceptance note names the browser, screen reader and versions, the action sequence and what was heard. If a result differs, the DOM publication history and tree capture can help locate the boundary. [Accessibility audit](accessibility-audit.md) and [Browser test guide](browser-test-guide.md) provide the wider review context.
