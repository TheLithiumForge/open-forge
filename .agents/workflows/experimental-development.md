# Experimental Development Workflow

## Goal

Complete a large, already-accepted development program within a constrained
execution budget without weakening contracts, evidence, or acceptance. The
Mastermind plans ahead, sends closed high-context implementation packets, inspects
the actual result, reproduces evidence, spots correctness and local-improvement
issues in the same Task space, and owns every phase transition and acceptance.

Use brilliant implementation capacity for contract-defining or still-foundational
work. After the shared structure and delivery pattern are solid enough that the
remaining change is closed execution, use the normal max-reasoning Luna
`implementer` for implementation and reserve the Mastermind for decisions,
integration, verification, and final judgment.

## Applicability

Use this experimental Workflow only when the maintainer selects it for a program
with an accepted architecture, a durable Task sequence, stable repository rules,
and scarce execution budget. It specializes rather than replaces the strict
[Development Workflow](development/_development.md): preserve its contracts,
evidence boundaries, coherent commits, public scenario, gate, and acceptance, but
do not require a separate agent for every phase or review lens.

Do not use the efficient path while a material product, architecture, contract,
safety, compatibility, platform, authority, or placement decision is unresolved.
Do not call a structure solid merely because one implementation passed tests.

## Roles And Routing

- The **Mastermind** owns the complete problem model, forward plan, architecture,
  authority, phase boundaries, detailed dispatch packets, exact-diff inspection,
  verification, improvement spotting, correction routing, commits, integration,
  and final acceptance. It never delegates an unresolved decision.
- The **brilliant implementer** owns closed work that defines or changes public or
  callable contracts, shared foundations, safety-critical invariants, or a
  structure whose pattern is not yet established. It is also the fallback when a
  normal implementation exposes a genuine plan gap rather than a local defect.
- The normal max-reasoning Luna **implementer** owns closed Red, Green, structure,
  Blue, Purple, configuration, documentation, and later command work after the
  Mastermind records that the applicable foundation and pattern are solid. It
  makes implementation-local choices only and does not reopen scope.
- Separate reviewers, writing reviewers, councils, and phase specialists are not
  default ceremony in this Workflow. Invoke a fresh lens only when the Mastermind
  cannot establish a consequential fact from the artifacts and executable
  evidence, or when one specifically identified risk justifies the extra cost.
  The Mastermind final spotter pass is always required.

## Steps

1. **Plan ahead.** Read the applicable authority and current Task state. Map the
   remaining Task sequence, dependencies, shared capabilities, likely change
   surfaces, focused evidence, full gate, public scenario, stop conditions,
   commit boundaries, and the point at which the shared structure becomes solid.
   Record material meaning before mutation.
2. **Classify the increment.** Use the brilliant implementer for contract or
   unresolved-foundation work. Use the normal Luna implementer only when outcome,
   authority, behavior, paths, protected surfaces, validation, non-goals, and stop
   conditions are closed. If the classification is uncertain, treat the work as
   foundational rather than spending a normal implementation run on discovery.
3. **Dispatch one complete packet.** Name the exact baseline, branch, objective,
   current architecture, accepted decisions, required behavior, allowed and
   forbidden files, direct consumers, frozen tests or production surfaces,
   commands, expected results, cleanup, evidence, return shape, and conditions
   that require `PLAN_GAP` or a stop. Avoid duplicate exploration already resolved
   by the Mastermind.
4. **Inspect actual work.** Read the changed and untracked files, targeted diff,
   direct consumers, contracts, and evidence. Never accept a helper summary in
   place of artifacts. Reproduce the smallest decisive focused checks, then the
   applicable integrated gate. Reject harness, fixture, warning, skip, or output
   anomalies instead of explaining them away.
5. **Run the Mastermind spotter pass.** In one bounded pass over the Task diff and
   immediate integration neighborhood, check correctness, contract agreement,
   safety, error paths, evidence strength, source locality, duplication,
   overlarge responsibilities, simpler control flow, maintainability, and the
   next command's cost. Distinguish blockers from high-value local improvements
   and from speculative cleanup.
6. **Dispatch corrections efficiently.** Send one grouped exact correction packet
   to the normal implementer for local implementation defects or spotted
   improvements within frozen meaning. Return to the brilliant implementer only
   when the callable contract or shared foundation must change. Return to the
   maintainer when a fundamental decision is exposed. Do not spend agents on
   repeated independent confirmation of already-reproduced facts.
7. **Accept and continue.** Update authoritative Task state, stage only intended
   paths, create the coherent phase or Task commit, and continue automatically to
   the next authorized increment. Preserve local-only, integration, release, and
   push boundaries from the active program.

## Efficiency Guardrails

- Prefer one complete implementation packet over several exploratory packets.
- Reuse established fixtures, command composition, shared result shapes, and gate
  commands; do not repeat repository-wide exploration for each command.
- Run focused evidence during implementation and reserve the full gate for a
  coherent accepted boundary unless the failure surface requires it earlier.
- Do not automatically invoke both correctness and improvement reviewers. The
  Mastermind combines those lenses in its final spotter pass and requests a fresh
  external lens only for a named consequential risk.
- Never save usage by weakening Red, skipping Native AOT or public evidence,
  changing an expectation in Green, hiding a platform skip, broadening authority,
  or accepting unresolved safety behavior.

## Completion

- The Mastermind recorded why the shared structure was or was not solid enough
  for normal Luna implementation and selected brilliant versus normal execution
  accordingly.
- Every implementation packet was closed, detailed, and bounded; no helper had to
  decide architecture, scope, contract meaning, or acceptance.
- The Mastermind inspected the actual artifacts, reproduced decisive evidence,
  completed one combined correctness and improvement spotter pass, and routed any
  material finding to the right owner.
- Required contracts, frozen evidence, public scenarios, full gates, coherent
  commits, integration boundaries, and final acceptance remained intact without
  mandatory duplicate review ceremony.
