# Supervised Luna Preparation Trial

## Goal

Evaluate whether a Luna/max Task Mastermind can reduce the cost and latency of
one closed preparation task while the user-facing Overseer retains program
architecture, sequencing, integration, and acceptance.

Use this Workflow only when the Task capsule selects it explicitly. It is an
opt-in experiment. It does not change Adaptive Development, Program
Development, Managed Worktree Project Development, the ordinary Task
Mastermind role, or the model used for consequential semantic work.

The first trial is preparation-only. It may inventory facts, identify gaps,
form a future execution capsule, and record revalidation triggers. It may not
implement production behavior or choose product, architecture, public wire,
safety, lifecycle, serialization, shared-placement, or test-meaning decisions.

## Steps

1. **Select a closed preparation boundary.** Use a task whose accepted outcome,
   source authority, protected surfaces, evidence questions, and stop conditions
   are already explicit. Reject the trial when supervision would require the
   Luna/max Task Mastermind to resolve semantic ambiguity.
2. **Freeze the task identity and base.** Record the permanent task ID and name,
   exact commit and tree, isolated branch and worktree when the trial writes a
   durable result, expected and protected paths, direct integration
   neighborhood, and the later gate that must revalidate the preparation.
3. **Assign one Luna/max Task Mastermind.** Give it a maximum of three bounded
   evidence workers. Each child receives one literal responsibility and remains
   read-only unless the Task capsule separately authorizes a narrow preparation
   record. The Task Mastermind supervises and synthesizes its children rather
   than forwarding their raw output.
4. **Load normal Open Forge context.** The experimental model does not relax
   context or authority rules. Every child that authors or reviews C# semantics
   independently reads the complete current `.agents/directives/csharp/_csharp.md`,
   `design.md`, and `style.md` files and reports fresh SHA-256 fingerprints.
5. **Produce one preparation result.** Record the current inventory, accepted
   versus missing capability, future command or change matrix, protected
   boundaries, stale-data risks, and exact revalidation triggers. Do not report
   future implementation or acceptance evidence as completed.
6. **Run one fresh Sol/xhigh review.** Review the complete preparation result for
   architecture, contract, evidence, scope, and false-green risk. Return all
   accepted findings to the same Luna/max Task Mastermind for at most one grouped
   correction. A second correction cycle ends the trial.
7. **Measure the experiment.** Record elapsed critical-path time, child count,
   handoffs, missing-context returns, accepted and rejected review findings,
   correction cycles, stale preparation, revalidation cost, gate failures,
   integration conflict, and any defect found after acceptance. Do not compare
   a preparation trial directly with a semantic implementation task.
8. **Return authority upward.** The Overseer decides whether the result is useful,
   advances project state, and selects any later implementation. A preparation
   result never authorizes its own mutation or integration.

Open the circuit breaker and return the Task when the Luna/max lane must choose
semantic meaning, overlaps another live semantic owner, changes a protected
surface, produces a missing or false-green receipt, needs more than one grouped
correction, receives a material architecture or contract failure in the final
review, or repeats the same infrastructure failure twice. A model-capacity or
availability fallback must be disclosed and does not count as evidence for the
requested model.

Quiet remains unobserved progress, not failure. The Overseer nevertheless ends
the experiment without accepting preparation when a running lane misses two
explicit checkpoint or return requests across separate supervision intervals.
This latency circuit breaker classifies the trial as uneconomic or unobservable;
it does not classify the Task, repository, or agent result as failed. Preserve
any returned evidence only if it arrives before termination and can be bound to
the frozen base.

## Completion

- The selected preparation result is committed coherently in its isolated lane
  when local commits are authorized.
- Production, tests, packages, CI, public contracts, and other protected
  surfaces remain unchanged unless a later Task explicitly authorizes them.
- One fresh Sol/xhigh review is dispositioned and no more than one grouped
  correction was required.
- The Task record contains the experiment measurements, limitations, and exact
  revalidation triggers.
- The default development Workflow and ordinary Task Mastermind remain
  unchanged.
