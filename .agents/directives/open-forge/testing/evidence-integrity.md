# Test Evidence Integrity

## Instructions

- Give every test stable, durable selection identity through the native runner or repository convention. Temporary Task names do not establish an enduring test boundary.
- Select evidence depth proportionately: direct evidence proves focused behavior, integration evidence crosses one real boundary, and end-to-end evidence proves a complete externally visible journey.
- Follow the [Evidence Tiers Pattern](../../../patterns/testing/evidence-tiers.md): keep Unit evidence cheap and focused over in-memory inputs, use Integration evidence for one real module or system boundary, and reserve EndToEnd evidence for complete black-box journeys through the delivered interface. Do not duplicate detailed lower-tier branch coverage at the system boundary.
- Test only behavior, contracts, artifacts, and effects owned by Open Forge. A third-party library, runtime, framework, package manager, or tool may be exercised as a real boundary, but it is never the subject of the test: assert only the Open Forge input, integration, delivery, and observable result that the task owns. Do not duplicate upstream behavior or preserve third-party internals as local contracts.
- Keep third-party boundary checks to what Open Forge needs: the package installed, the delivered command runs, and our inputs and outputs are correct. For example, invoke the installed command rather than asserting how npm implements its command links. Test our own parsing, selection, and cleanup rules directly; do not expand these into tests of the underlying tool.
- During Preflight, explicitly select the evidence tier and independently runnable project path for every planned test command. When a test surface has multiple projects, project-level tier separation is required; traits and filters are orthogonal selection within a project, not a substitute for the project boundary. Node repository scripts that share one compiler environment may use independently runnable test files and package commands for tier selection. A compiler configuration need not duplicate that execution boundary. This exception does not change C# test-project separation.
- Keep the durable acceptance summary and exact reproduction commands in tracked task/checkpoint records. Generated binaries, raw logs and full machine reports may be disposable outputs; no required test, fixture, helper or task state may exist only in an ignored output directory. Deleting outputs requires a fresh run before claiming fresh execution evidence.
- Preserve a canonical execution receipt for every acceptance gate. Bind it to the working root, source and configuration identities, commit and tree when available, exact command and toolchain, runtime target and execution mode, fresh artifact identity, selected, discovered, and executed counts, failures, skips, warnings, exit status, and known limits.
- When one test population can run against more than one runtime target, keep the targets as separate results rather than separate test populations. Each target proves the failures only it can expose, and a pass on one target is never evidence for another. Name the target in the receipt and in any claim that a gate is green.
- Treat execution cost as a selection decision the same way evidence tier is. Record which mode a gate runs in, what it costs, and why a cheaper mode cannot prove it. A suite that is slow because it is serialized, rebuilt, or over-tiered is a defect in the evidence design, not a fact to work around; fix it at its cause instead of quietly narrowing coverage or skipping the gate.
- Change a runner's parallelism or isolation default only on repeated qualification evidence that the same population selects, executes, and reports identical results with no cross-test contamination, flakiness, stale artifact, or zero-test selection. Measured speed alone does not authorize the change, and a suite that cannot meet the isolation contract stays serialized with a written reason rather than weakened assertions.
- Treat exit zero as one fact rather than sufficient proof. Zero discovered or executed tests, a stale `--no-build` artifact, skipped required tests, warning-bearing or partially loaded clean output, and a wrong-scope negative search cannot prove the positive gate they appear to cover.
- Name tests by durable behavior, scenario, and expected outcome. Cover the accepted happy, invalid, boundary, failure, and interruption paths at the cheapest tier that proves them, and keep focused selections quick and easy to run without incidental network access, timing sleeps, or unrelated setup.
- Parallel tests own every mutable workspace, home, temporary directory, cache, build output, port, and external fixture they can affect. Shared state is read-only unless an explicit synchronization contract proves otherwise.
- Never let a test read or write a real per-user location. Redirect every product store that lives outside the workspace — known folders, caches, lock and recovery stores — into a directory the test owns and deletes. Do this once in shared test support, not per fixture: duplicated redirection drifts, and the copies stop agreeing about the layout. When one process runs its collections in parallel, set the redirection before any test runs rather than per test. A suite that shares one real per-user store cannot be isolated by serializing it: the state still outlives the run, so fix the redirection instead.
- Environment variables do not relocate every platform. Windows resolves known folders through the shell and ignores `%LOCALAPPDATA%`, so a product that must be relocatable for tests provides an explicit override and the tests use that. A fixture never recomposes the product's storage layout, path identity, or hashing to reach around a missing seam; add the seam to the product. One shared test oracle may restate the layout so that a product change fails loudly, but several fixtures restating it is duplication that hides the change.
- Keep path namespaces explicit in every test. Use slash-separated workspace-relative strings only for logical or canonical paths. Build physical or host-absolute paths with .NET path APIs such as `Path.Combine`, `Path.GetFullPath`, `Path.GetTempPath`, `AppContext.BaseDirectory`, or the relevant `Environment.SpecialFolder` known folder; never hard-code POSIX roots, `/private` prefixes, drive letters, or host separators into physical fixtures. Prefer the `TemporaryWorkspace` relative-path APIs and derive expected absolute paths from the same owned root. Let the runtime choose platform locations — `Directory.CreateTempSubdirectory` for an owned temporary directory — instead of composing one from a temporary root and a generated name. When a test covers lexical-versus-physical identity or filesystem capability, compare values resolved by the same platform-aware API or probe the capability instead of comparing raw strings from different path namespaces.
- Keep ordinary test execution read-only with respect to generated expectations and other review baselines. An update action is explicit, targeted, serial, and reports its exact mutation.
- Use a focused snapshot when a stable exact string, structured projection, or large reviewed result is clearer than a train of assertions. Keep safety invariants, state transitions, and destructive-effect boundaries as direct assertions, and never broadly normalize a snapshot until it stops proving the contract.
- Allow multiple focused, explicitly named snapshots within one test and test suite. Keep each tied to its scenario, step, and output view. Use snapshots for exact prose or serialized output rather than arbitrary string literals, substring checks, or trains of magic-string assertions. Use direct assertions for semantic facts, independently observed effects, preservation, and state transitions; a reviewed snapshot never proves those by itself.
- Prefer real boundaries and observable resulting state. Introduce a test double only when the real boundary cannot be exercised safely and deterministically, and keep that reason local.
- Invalidate evidence from the earliest changed input boundary and in proportion to its consumers. A local implementation change first invalidates focused evidence. A shared or public contract, composition, configuration, generation, native, package, serialization, or embedded-resource change invalidates the broader dependent evidence that consumes it.
- For behavior-preserving structural work, add semantic or differential evidence for consequential facts. Compare applicable presence and absence, ordering, nullability, effects, findings, recovery or interruption state, and public bytes instead of relying only on compilation and unchanged test counts.
- Build test data from small composable seeds, builders, and factories that expose the scenario's meaningful choices. Begin them beside their consumer; promote only identical semantics to the nearest common test scope after demonstrated reuse. Prefer assembling a scenario from focused capabilities over inheritance, a universal fixture, a generic repository, or an options bag that hides which facts the test needs.
- If an applicable Purple test-improvement phase is selected, inspect duplicated real temporary-directory, workspace, and process helpers. Promote a shared real-temp support source only after at least two real test projects or fixtures need identical semantics, place it at their nearest common scope, and keep it out of production. Do not create a generic `Utils` bag or a fake filesystem.
