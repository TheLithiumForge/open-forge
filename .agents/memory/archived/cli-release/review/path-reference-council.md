# Path, Reference, And Discovery Council

## Status

This is contextual council synthesis. It does not accept a command, flag,
schema, or implementation. The linked designs record reviewed outcomes and the
details that remain in the maintainer review queue.

Later maintainer feedback accepts Discovery as a manually organized help and
documentation section, one reference operation with separate incoming and
outgoing result sections, `route list` for bounded structural neighborhoods,
ordered Context paths, global compact and expanded human views, and no graph or
separate neighborhood command. The linked designs and `CLI-D076` through
`CLI-D085` record the current disposition and remaining details. This council
preserves earlier evidence rather than a competing current recommendation.

## Decision Frame

The council examined which distinct jobs deserve public surfaces among:

- Ordered path-only context results.
- Incoming and outgoing ordinary local references.
- Route-neighborhood paths.
- Cheap graph views or queries.
- Complete routed-material cataloguing.
- An easy-to-find discovery category or first-contact operation.

The evaluation criteria were practical agent value, fewer reads and tool calls,
deterministic completeness, bounded context cost, shallow CLI paths, exact
relationship types, and no inferred relevance or hidden persistent truth.

## Verified Current Boundaries

- [`context`](../../../crystallized/documents/cli/contracts/context/_context.md) returns ordered startup,
  continuity, and selected-route logical sources. It emits overwrite layers and
  explicitly link-expanded sources. Its accepted `metadata` part exposes
  CLI-generated source facts, while its accepted `paths` part exposes the exact
  ordered physical layers without authored content.
- [`find`](../../../crystallized/documents/cli/contracts/find/_find.md) returns flat `.agents` Markdown inventory
  and exact tag or heading predicates. It includes routed and unrouted sources
  and intentionally omits route hierarchy.
- [`route inspect`](../../../crystallized/documents/cli/contracts/route/inspect/_inspect.md) reports one source's route
  chain, depth, parent, counts, loading behavior, inherited Axioms, overwrite,
  and context cost. It intentionally omits a workspace route list.
- A recognized `entrypoint` makes its folder routable. Authored files and source
  contracts establish direct routed children. Descriptions and tags help select
  those routes but do not create route membership. Generated `Entries` are
  derived navigation and cannot add or hide routed sources.
- Ordinary Markdown links, route relationships, loading relationships,
  overwrites, and generated navigation are different facts. A link never creates
  loading or authority.
- Current accepted operations use per-invocation derived facts. They do not
  require a persistent search or graph index.
- A reached bound or incomplete scan must remain visibly `incomplete` or
  `blocked`. The current result model does not need a new `truncated` semantic
  status merely to represent a limit.

Archived CLI-v2 route and reference inventories support the feasibility of
shared invocation-local facts, source locations, cycle termination, and
consumer-specific projections. They remain historical raw evidence and do not
control current product design.

## Independent First-Round Perspectives

### Cold Outsider

The outsider separated three clear jobs: path-only `context`, direct incoming or
outgoing references, and direct route neighborhood. It rejected a general graph
because the question, edge types, depth, and limits were undefined.

### Framework Operator

The operator kept context and route-neighborhood paths as projections of their
current domain operations. It supported a standalone direct-reference operation
and allowed only an optional fixed one-hop typed graph view if combining results
from different operations later proved costly.

### Agent Workflow

The workflow lens prioritized metadata-only calls that avoid reading bodies. It
recommended context and route-inspection path projections plus one scoped direct
reference operation. It rejected a general graph product.

### Radical Simplifier

The simplifier accepted only one new standalone job: direct references. It kept
paths as projections, rejected graph commands, and required evidence before any
multi-hop or mixed-edge expansion.

## Route Catalogue Council

All perspectives identified one missing operation: an atomic,
machine-readable enumeration of authored routed topology. `find` is flat and
includes unrouted sources; `route inspect` is single-subject; recursively reading
generated Entries is neither atomic nor authoritative.

The disagreement concerned filters. Some perspectives supported exact own-tag
or literal metadata filters. Others kept tag discovery in `find` and limited the
route catalogue to exact subtree and depth. No perspective supported fuzzy,
semantic, inherited-tag, or invented scope filtering.

## Discovery Categories Council

This section preserves pre-feedback perspectives. The maintainer later accepted
manually organized help and documentation only and rejected a `discover` command
or executable manifest. The historical alternatives below are not live
fallbacks.

The council agreed that Discovery should be prominent in root help and should
cross-list the operations that report each fact. It disagreed about a canonical
`discover` namespace:

- The discoverability lens supported `discover routes|references|neighborhood` as a visible
  read-only family.
- The operational-interface lens supported a thin executable `discover` capability and current-state
  manifest while leaving domain commands canonical.
- The Framework-semantics lens supported an organizational family but warned that each operation needs a
  distinct schema and meaning.
- The simplifier rejected a canonical family and preferred a root-help category because a
  namespace could become a miscellaneous inspection bucket.

A focused adversarial rebuttal argued that help alone might not satisfy
autonomous agents and recommended a thin executable manifest. The maintainer
rejected that fallback. The accepted response is to test manually organized
help while each domain operation remains responsible for runtime coverage and
complete-empty results.

The configured `challenger` agent could not start because its updated model
identifier was unavailable. An independent advisor supplied the focused
adversarial rebuttal instead. This operational issue did not change the product
evidence.

## Current Disposition Of Council Topics

The maintainer resolved the council topics as follows. The linked Decision
Agenda remains the accepted record; this list only reconciles the earlier
evidence with that direction.

1. Keep each fact's definition and reporting behavior with its domain operation.
2. Use `route list` for authored routed topology. Root selection, omitted depth,
   and first-version metadata filters remain open under `CLI-D084`.
3. Use the `paths` Context content projection for exact ordered physical layers.
4. Use one direct `references` operation with separate incoming and outgoing
   sections. Scan scope, direction-filter spelling, and external outgoing-link
   defaults remain open under `CLI-D085`.
5. Do not add a separate route-neighborhood or graph operation.
6. Organize Discovery manually in help and documentation. Do not add a
   `discover` command, namespace, executable manifest, or runtime fallback.

## Historical Material Dissent

- A fixed one-hop typed graph neighbor view might save several calls. The
  simplifier argues that it still duplicates route and reference operations.
- Exact route tag filters could make `CLI` or `Pattern` discovery one call. The
  stricter view says this duplicates `find` and risks confusing tags with route
  meaning.
- A canonical `discover` namespace is highly visible, but it adds another path
  and may become ceremonial. The maintainer rejected the namespace and thin
  manifest despite this historical dissent.

## Evidence Needed

- Run fixed cold-start tasks for source, route, reference, and context-path
  discovery. Record silent omissions, first-attempt success, tool calls, reads,
  output size, and context cost.
- Verify route-catalogue fixtures with zero missing or extra routed rows under
  stale Entries, detached trees, collisions, and incomplete metadata.
- Verify incoming references against a hand-authored expected edge set and fail
  any run that reports a complete empty result after an incomplete scan.
- Compare compact context metadata and paths output. Verify identical resolver
  order and status while the paths projection materially reduces output.
- Test representative mixed-edge workflows with focused route and reference
  operations without introducing a graph result.
- Verify that manually organized root help, structured help, and completion
  derive from one command-definition source.
