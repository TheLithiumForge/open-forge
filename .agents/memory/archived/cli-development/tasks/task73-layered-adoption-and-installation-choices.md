## Analysis Findings And Recommendation

Analysis selected by the maintainer and carried out on 2026-10-02 in the
isolated `docs/cli-simplification` worktree. The recommendation is to explain
three useful layers, offer optional installation presets backed by existing
exclusions, and qualify local Memory separately before offering Git ignore
defaults. These are proposed changes; the current installation default and
agent behavior have not changed.

### What Already Works

The installed Framework already separates existence, relevance, and authority.
Most categories start empty, nested scopes load when selected, Extensions are
optional, and Memory states are distinct meanings rather than maturity levels.
The smallest layer can therefore use the same Markdown and routing model as
the larger layers. It does not need a second agent engine or a new runtime
mode. A fuller installation does not itself supply workers, tools, or a harness.

The current settings already support `removedCategories`, `removedDirectories`,
and `removedFiles`. `FrameworkPayloadSelection` and `WorkspaceRemovals` apply
those choices to installation, update, and Extension destinations. A directory
exclusion also covers future descendants. Generated navigation reflects the
remaining routes. Missing required ancestors block the plan rather than being
silently restored.

### Proposed Layers

| Layer                  | Explain it as                                         | First useful action                                       | Add the next layer when                                        |
| ---------------------- | ----------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| Essentials             | Give your agent rules and links it can follow         | Add one recurring correction and link an existing source  | You need to resume work or preserve accepted knowledge         |
| Continuity             | Keep useful work and accepted knowledge between tasks | Save a short Working note or a Crystallized record        | You need a repeatable method, richer planning, or coordination |
| Coordinate when needed | Add only the capabilities this project needs          | Select a relevant Workflow or Extension for one real task | A further capability has a concrete use                        |

Essentials and Continuity are candidate installation presets. A complete base
and custom choices remain available. The coordination layer should not mean
“install every Extension”: optional collaboration, planning, development, and
orchestration packages remain selectable. Existing host tools and permissions
still determine which actions an agent can perform.

Keep the first installation-preset increment opt-in and preserve current
unqualified and `--automatic` installation behavior. Whether Essentials later
becomes the first-install default is a separate maintainer decision supported
by comprehension and compatibility evidence. A preset should resolve to visible
concrete settings once, rather than storing a second authoritative `mode` that
can disagree with the workspace files.

### Documentation Controls

Use one explanation with progressively revealed detail. Begin each onboarding
page with purpose, a concrete example, and the next action. Use **Quick view /
Full explanation** as a presentation control; identify it as changing only the
page. Show the next capability by need, not by requiring the reader to learn the
full category taxonomy first.

Start with native `details` sections on the introduction, installation, first
task, growth, and CLI overview pages. They already work in the site and keep
the repository Markdown readable. Keep prerequisites, command syntax, the
compact flag inventory, write effects, and any required confirmation visible.
Put rationale, deeper mechanics, full diagrams, and longer examples behind
the controls. Use the same three-layer narrative in the demo and diagram.

A shared site-wide control can follow if per-page controls prove insufficient.
Use a small typed component/provider in the existing Docusaurus app, retain one
content source, and make full explanations directly linkable. Support keyboard
operation, mobile layout, static rendering, search, and links into closed
sections. Returning to Quick view must not hide the active anchor or an
instruction needed for the next action. The complete reference remains directly
accessible. Neither view changes an installation or relaxes required rules.

### Installation Choices

Use understandable outcomes in the wizard, with category names and Memory
states available under customization. Keep file creation, loading, and Git
tracking separate:

- **Not installed:** excluded routes and their children stay absent through
  Update. Preserve required loader/host anchors and selected parents.
- **Installed:** readable Markdown exists. Existing tags, scope selection, and
  explicit rules determine what loads; being installed does not load all leaves.
- **Shared or local:** Git policy controls sharing, without changing authority
  or whether an existing local file can be read.

Retain the requested CLI Skill in the proposed useful presets. If custom
choices permit disabling Skills, generated authored rules must not leave a
mandatory link to a missing CLI Skill. Similarly, selected Memory states need
the Memory parent, and Extension recipes must not assume disabled destinations
exist. Agents need an explicit readable rule to respect omitted destinations
rather than recreating them during ordinary continuity capture.

The native `planning` Extension preview on the custom Crystallized-only shape
returned success with 14 `extension-install.path-excluded` findings. It selected
the `workflows` dependency while excluding planning routes and Templates.
Current package dependency closure therefore does not guarantee that all of a
package's advertised capabilities are present. The new installer must explain
these conflicts before claiming a complete capability. Recommend offering a
reviewable expansion plan or a different package selection. Do not silently
enable excluded categories or substitute one Memory state for another.

The settings write, payload effects, generated Entries, ownership publication,
and selected Extension effects need one revalidated mutation plan. Preview
must expose the exact exclusions and effects; cancellation writes nothing.
For existing installations, changing a preset must retain authored files and
overwrite companions. Disabling future installation and deleting existing
content are separate actions. Re-enabling a route removes its exclusion and
lets Update restore the appropriate default, as demonstrated by the expansion
probe. Do not reuse Install as an implicit replacement/update command.

### Local Memory And Git Tracking

Ignoring `memory/working` did not change Context loading, with or without a Git
repository. However, copying only the files Git would include left a tracked
Memory entry pointing at a missing Working entrypoint. Doctor returned exit 2
with five findings. Ignoring only the note while retaining its entrypoint still
left a generated link to the absent note: Doctor returned exit 2 with three
findings. These were fresh-copy simulations without Git commits.

Consequently, adding `.gitignore` patterns is insufficient for a coherent
local-Memory feature. Shared navigation must not depend on another person's
absent local records. Local records still need ordinary readable state, scope,
and discoverability. The current overwrite contract explicitly gives generated
Entries to the base entrypoint, so an overwrite cannot simply become a second
local generated catalogue.

Recommend retaining current tracking behavior in the first preset increment.
Before offering **Keep Working notes local**, select a design for optional local
navigation that preserves shared navigation across a fresh checkout. Compare a
fully local Framework with a shared Framework plus local records; state what
bootstrap each requires. A design that introduces layered local navigation
needs explicit routing and generated-navigation contract changes and evidence,
rather than being hidden inside an ignore-rule patch.

When qualified, tracking changes should edit only a bounded owned section in
the selected ignore file, preserve other rules, and leave the Git index alone.
Already tracked files stay tracked until the user chooses a separate untracking
action. Validate effective ignore behavior, nested scopes, shared accepted
knowledge, fresh checkouts, and setup on another machine. Git ignoring does
not disable Memory loading.

## Implementation Sequence

1. **Explain the layers.** Update the onboarding narrative and simplified
   diagram, add progressive detail controls, retain the complete flag reference,
   and qualify one first-task journey at each layer. Start with the existing
   page-level controls; add a global preference only for a demonstrated need.
2. **Freeze the installation interface.** Define opt-in Essentials, Continuity,
   complete-base, and custom selection; settle exact flag grammar and wizard
   behavior. A candidate `install --preset essentials` spelling is proposed
   only and is not a current CLI option. Define the existing-workspace expansion
   journey separately and keep automation inputs explicit.
3. **Implement selection through existing settings.** Extend Install binding
   and planning, settings mutation, generated navigation, and the minimal plan
   review. Derive selectable destinations from the actual payload. Keep
   exclusions as the persistent source; do not introduce another mode registry.
4. **Qualify Extension interactions.** Resolve or visibly reject incompatible
   capability selections, preserve explicit omissions, and test nested parent
   requirements. Synchronize applicable Framework defaults, loader/Skills/Memory
   instructions, Maintenance, install/update/Extension contracts, help, the CLI
   Skill, and public documentation after the behavior is accepted.
5. **Design and prove local Memory.** Resolve the shared/local navigation
   boundary before adding Git ignore defaults. Then implement bounded tracking
   edits and qualify fresh-checkout behavior. This can ship independently of
   the earlier documentation and preset increments.
