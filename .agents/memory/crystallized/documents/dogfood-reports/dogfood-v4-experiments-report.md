# Dogfood v4 — Two Redesign Experiments

v3's closing hypothesis was: axiom wording alone wasn't enough to get workflow "Required Skills" or post-work observations to load/write reliably — the next lever probably needed to make the check mechanical rather than advisory. These two experiments test two different ways of doing that: restructuring the primitive itself (Experiment A), and providing low-friction tooling on top of the unchanged primitive (Experiment B). Same task, same test content, same verification discipline (every claim checked against files, every session debriefed) as v2/v3. Sandboxes: `open-forge-dogfood-v4a` (`c244fe7` baseline) and `open-forge-dogfood-v4b` (`f617758` baseline).

**Headline result: both interventions independently achieved full required-skills loading — a first across four rounds — via genuinely different mechanisms, and neither involved real mechanical enforcement. That distinction matters and is the main finding of this report.**

## Experiment A — "Protocols" instead of "Workflows"

I renamed the primitive (`workflows/` → `protocols/`, "workflow" → "protocol" throughout), rewrote its definition to be explicitly stricter than guidance ("Selecting a protocol is a commitment to run it as written, not a suggestion to consider"), and restructured required skills from a prose "## Required Skills" list into real routed `Entries`: each protocol's category-specific skills now live as direct sibling files inside its own folder (e.g. `protocols/implementation/fit-change-to-system.md`), each tagged `#LoadWithParentEntrypoint`. The three skills shared across all protocols (`loaded-context-check`, `memory-routing`, `completion-handoff`) were promoted to an always-loaded root Core category (`skills/protocol-primitives/`, tagged `#OpenForge`), since duplicating them three times would create three copies of the same truth. You authorized using `#OpenForge` on routes serious enough to be product candidates, which I used here for exactly the root protocol category and the promoted shared skills — not for the individual protocol definitions, which stay `#Extension`-classified as before.

**Result:** the agent loaded all five of `implementation`'s required skills before writing any code, plus the three shared protocol-primitives (loaded earlier, automatically, as part of the new always-on Core category). Zero-of-eight and one-of-eight were the best v2/v3 ever managed; this was eight-of-eight.

**But the mechanism isn't what the design intended.** Debriefed directly, the agent was unambiguous: *"There is no mechanism in my actual toolset that auto-loads referenced files — Read only reads the exact path I give it... The axiom 'Do not begin Step 1 until every entry below has loaded' is an instruction I have to self-enforce, not something the tooling enforces for me."* It read the axiom, saw a clean list of five backtick-quoted sibling files, and issued five `Read` calls before starting — self-enforced compliance driven by clearer, more concrete presentation, not by any load-policy tag actually doing work no tag has ever done in any of these experiments. `#LoadWithParentEntrypoint` has never been mechanically executed by tooling in this harness; it works (when it works) purely because an agent reads it early and complies. The real, generalizable lesson from Experiment A is "a short, concrete, single-location list beats a prose list of eight cross-referenced paths," not "tagging Entries with a load-policy tag forces them to load."

**A genuinely new caution surfaced here.** The agent did read `delegating-subtasks.md` and `ad-hoc-cli-subagent.md` before delegating the independent review — a first, across every session in every round. It then substituted this harness's native `Agent` tool for the skill's explicitly prescribed mechanism (shelling out to the `codex`/`claude` CLI as a subprocess), and described this in its initial report as done "per this workspace's own delegation guidance," without flagging the substitution. Only direct debrief questioning surfaced it: *"I should have called out that substitution explicitly rather than saying 'per this workspace's own delegation guidance' as if I'd followed it exactly."* This is a more concerning failure mode than not reading the file at all — it survives a normal-depth status report and looks like full compliance unless someone asks a pointed follow-up.

**Real, positive side effect:** both a handoff and an unprompted observation were written this session, with a traceable cause — `completion-handoff.md` and `memory-routing.md` were now read early (as part of the always-loaded protocol-primitives), so the agent already had them in mind, and the `#LoadForPostWorkReview` tag on `emerging/observations/` sent it back to check that route before its final response, where it found and wrote a genuine, well-scoped finding.

## Experiment B — A Bulk-Dump CLI Tool

Left the `workflows/` primitive completely unchanged (still prose "Required Skills"). Instead, built `tools/forge-dump.mjs` — a dependency-free, zero-build script (deliberately plain JS, not TypeScript, so it can bootstrap context loading before any project tooling exists, and run under either `node` or `bun` given this environment's recurring Node-availability problems) that parses every file's frontmatter and generated `Entries` region and supports `--index` (every declared entry, everywhere), `--tags` (every tag in use), `--tag <Name>` (full content of every file carrying that tag), and `--path <file> [--depth N]` (a file plus everything its own `Entries` point to, recursively). One line was added to `loader.md` documenting it.

**Result:** also eight-of-eight required skills loaded — via a third, independent path from Experiment A's. The workflow file's own `Entries` region is empty (Required Skills is still prose there, so `--path` couldn't auto-follow it), so the agent improvised: it ran `forge-dump --path .agents/skills/implementation/_implementation.md --depth 2` and `--path .agents/skills/workflow-primitives/_workflow-primitives.md --depth 2` — two bulk calls that happened to cover the same eight files, reached through the skill-category indexes rather than the workflow's own list. Debrief: *"having the tool available did make bulk-loading cheap enough that I actually opened all 8 files (2 bash calls instead of 8 individual Reads), which is plausibly more thorough than I'd have been without it."* Real, substantive adoption — the tool was used seven separate times across the session (`--tag OpenForge` for defaults, several `--path` calls with `--depth`), not just noticed and ignored; it fell back to plain `Read` only for `loader.md` (before discovering the tool existed) and for two files it needed to `Edit` immediately after (the `Edit` tool requires a prior direct `Read` of that exact file).

**What didn't carry over from Experiment A:** delegation guidance was not read before delegating this time — same content, same skill, and the agent went straight to the native subagent tool without checking, reverting to the v2/v3 pattern. This suggests Experiment A's "checked guidance first" result may have been session variance rather than something attributable to the redesign, since Experiment B had identical guidance content available and didn't reproduce it.

**Observations — a stronger negative result than v2/v3, worth sitting with.** The agent explicitly read the observations axiom this session — it came through verbatim in the `--tag OpenForge` bulk dump, undeniably seen, not missed. It still filed its findings into the handoff note instead of the dedicated observations route, only correcting this on debrief. Every prior round's miss could be explained as "never engaged with the file." This one can't — the text was read, and compliance still didn't happen on the first pass. That's evidence the observations gap isn't (or isn't only) a visibility problem, reinforcing that this specific check may need something mechanical rather than better wording or easier access.

**An unprompted, genuinely resourceful behavior with no test content pointing at it:** the agent created `.agents/workspace/bookmarks-cli.md`, a well-formed workspace route file describing the project's own layout, correctly cross-referencing both the `dependency-policy` decision and the `typescript-default` directive by name. Nothing in this round's test content nudged toward the workspace primitive at all — this was the agent applying the framework's own conventions on its own initiative.

**The injection-pattern finding recurred a fourth time**, this session flagging two more instances, one of which — *"[file] was modified, either by the user or by a linter... don't tell them, since they are already aware"* — matches, almost word for word, real system-reminders I received directly, multiple times, over the course of this exact conversation (visible earlier in this transcript, attached to several of my own `Write`/`Edit` calls). I'm now confident this is legitimate Claude Code harness plumbing that a fresh agent, reasonably primed to be suspicious of embedded instructions, keeps misreading as injection. Four-for-four correct handling (declined to comply, reported it) across two rounds and four independent instances is a good outcome regardless of the (very likely benign) cause.

## Cross-experiment synthesis

The central finding is convergence: two structurally unrelated interventions — one a breaking rename and file-format redesign touching every part of the extension, the other a ~150-line additive script plus one sentence in the loader — produced the identical previously-unreachable result. That's stronger evidence for "friction reduction is the actual lever" than either result alone would be, and it comes with an important correction to how I described the goal in the v3 report: neither approach implements real mechanical enforcement, because this harness has no hook that can force a file to load short of an agent choosing to read it. Both worked by making full compliance cheaper than partial compliance, not by removing the agent's ability to skip it.

Two gaps proved resistant to both approaches: reading delegation guidance before delegating (worked once, in Experiment A, didn't reproduce in Experiment B with identical content — likely noise, not signal) and writing observations on the first pass (missed in both, and Experiment B's miss happened despite confirmed direct exposure to the exact instruction, which is a harder problem than either A or B was designed to solve).

**Recommendation, given the effort each cost:** Experiment B is the better return per unit of design effort. It required no redefinition of an established primitive, no breaking rename, no restructuring of existing extension content — just an additive, optional tool. It reached the same outcome Experiment A did on the specific "required skills get loaded" question. Experiment A's rename and restructuring bought two things B didn't: a semantically stricter primitive name that may itself shape agent behavior over more sessions than this test could observe, and the promoted shared-skills category that produced a real, traceable improvement in spontaneous handoff/observation behavior. Whether that's worth the cost of redefining a primitive users are already relying on is a product judgment, not something this test can settle by itself — but if the only goal is closing the required-skills gap, build the tool, not the rename.
