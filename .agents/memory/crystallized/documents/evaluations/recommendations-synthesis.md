# Open Forge — Synthesis and Recommendations

Everything below is grounded in six rounds of evidence: the initial static critique, `recommendations-general.md`/`recommendations-open-forge-native.md`, the v2 and v3 dogfood compliance reports (testing two successive framework updates against identical tasks), and the v4 experiments (two competing redesigns I built and tested myself). Where a claim traces to a specific round, I say so. This is the capstone — read it as "what we actually learned," not a fresh theory pass.

## The one finding everything else sits on top of

**No load-policy tag in this framework — `#OpenForge`, `#LoadWithParentEntrypoint`, `#LoadForPostWorkReview`, or a restructured "required skills as Entries" — is ever mechanically enforced.** Every single one of them works, when it works, because an agent reads the tag's stated meaning and chooses to comply. This was confirmed directly, on the record, by a debriefed agent in Experiment A: *"There is no mechanism in my actual toolset that auto-loads referenced files... The axiom is an instruction I have to self-enforce, not something the tooling enforces for me."* This isn't a flaw exactly — it's the direct, honest consequence of the framework's own "no hidden runtime, plain files only" philosophy, which is a value worth keeping. But it means every design decision from here down should be evaluated as "does this make compliance cheaper/more natural for a self-enforcing agent," never "does this force compliance." Some of the framework's own governance wording ("must be loaded") reads more like an enforcement claim than that — worth tightening (see Wording, below).

## Structural recommendations

1. **Ship a "shared skill" pattern.** Building Experiment A, I hit a real gap: three protocols each declared three identical shared skills as required. There's no sanctioned way to express "this content is genuinely cross-cutting, used by every instance of this primitive, but isn't Core scaffolding" — I had to improvise by promoting it to a root Core category tagged `#OpenForge`, which stretches the framework's own rule that `#OpenForge` is reserved for Core. Extensions currently have no sanctioned way to say "load me by default within my own scope." Recommend either a documented convention for this (a `shared/` sibling category pattern with clear rules) or a new, narrower load-policy tag scoped to "default-loaded whenever this specific extension is active," distinct from `#OpenForge`'s "default-loaded always."
2. **Promote the directives category's own loading rule as the reference pattern for anything that needs real reliability.** Across every round, the one thing that worked 100% of the time, every session, no exceptions, was: *"Every directive file beside this entrypoint is workspace-wide; load all of them"* — an unconditional category-level rule, not a per-file tag an agent has to notice and individually apply. Compare this to Required Skills (a per-file list that got skipped 6 of 8 times before restructuring) or Observations (missed on first pass in 4 of 4 tested sessions, even with direct textual exposure confirmed). Where a category truly needs full compliance, model it on directives' "load everything here, no judgment call" shape instead of relying on tag-by-tag opt-in.
3. **Ship `forge-dump`-equivalent bulk reading as a first-party CLI feature**, not a per-project script users have to reinvent. Experiment B built a ~150-line dependency-free tool (`--index`, `--tags`, `--tag <Name>`, `--path <file> --depth N`) and it produced the same full-compliance result as a much larger structural rewrite (Experiment A), at a fraction of the design cost, with zero changes to any existing primitive. This is the single highest-leverage, lowest-risk thing to build next. Natural fit as `open-forge dump --tag X` or similar, consistent with the CLI's existing `install`/`extend`/`index` shape.
4. **Reconsider Observations as currently specified.** This was the least reliable primitive in every round tested — including a case in v4B where the agent had *provably* read the exact "write it before final response" instruction (via bulk dump) and still filed the finding elsewhere on first pass. Wording fixes (v3) didn't help. Structural fixes (v4A/B, indirectly, via better presentation elsewhere) didn't reliably help either. Either accept it as a best-effort, low-priority primitive and stop implying it's dependable, or give it a genuinely different mechanism — e.g., folding it into sessions (which had a working "low-friction fallback" framing added in v3 and never had a compliance problem) rather than keeping it as its own separate, easy-to-forget route.
5. **Give directives an explicit scope boundary.** The one directive that produced unpredictable results across every round wasn't a workspace-content rule — it was a rule governing the agent's own communication persona toward the user (chat-tone/caveman-speech). Sessions split roughly evenly between full compliance and explicit refusal-as-suspected-injection, for defensible reasons on both sides — this class of instruction sits close to what safety-trained agents are built to resist, and that's true regardless of how it's worded. Every directive governing work product, process, or technical defaults (TypeScript-by-default, no-unsafe-code, dependency policy) worked reliably, every round. Recommend the framework state explicitly: directives govern work, not persona; communication-style requests belong outside the directive mechanism entirely (if they belong anywhere).

## Wording recommendations

1. **Stop implying mechanical enforcement in governance language.** Phrases like "must be loaded" and "is load-bearing" (both used to describe the current tag system) read as claims about tooling behavior that don't exist. Suggest reframing throughout as what's actually true: "a compliant agent loads this," "this instruction is mandatory for an agent following this framework's rules" — honest about the fact that compliance is always self-enforced, never assume the reader will infer that distinction from the word "must."
2. **Close remaining "creating parallel truth" ambiguity wherever it still exists.** The v1 finding (an agent read the loader's caution against creating new memory states and misapplied it to justify skipping a routine handoff write) got a real, effective fix in the v2 diff — but it's worth an explicit pass checking whether the same ambiguity (a broad caution being misapplied to block a narrow, ordinary action) exists anywhere else in the framework's phrasing, since this specific failure mode — an agent using cautious wording as a permission-shaped excuse — was real and cost a full round to catch.
3. **Concrete, single-location lists beat prose lists of cross-referenced paths**, confirmed directly by Experiment A: rewriting "Required Skills" from eight prose bullet points naming files in a different folder tree into five backtick-quoted sibling filenames in the same folder measurably changed agent follow-through, even though the underlying enforcement mechanism didn't change at all. The transferable result is direct, colocated routing rather than backtick syntax; apply it through canonical relative Markdown links whose labels describe the target.

## Deduplication

- **Shared skills across protocols/workflows** (see Structural #1) is the clearest current duplication risk — the framework's own `extensions.md` already warns against this ("shared behavior must not be duplicated"), but provides no mechanism to avoid it beyond "put it in one pack," which doesn't solve the "used by three siblings within the same pack" case I hit directly.
- **`#LoadWithParentEntrypoint` and `#OpenForge` co-occurring on the same entries** (e.g. `directives/_directives.md`, `memory/_memory.md` carry both tags post-v2) is functionally redundant now that `#OpenForge` alone forces the load — harmless, but worth a one-line decision on whether that's intentional belt-and-suspenders or leftover, so a future reader doesn't wonder if there's a meaningful difference.
- **No other real duplication found.** The memory taxonomy (working/emerging/crystallized/archived, with their sub-states) looked like a duplication/overlap risk on paper in the original critique, but nothing in four rounds of dogfooding surfaced agents actually confusing or double-writing across those states — that concern didn't materialize in practice and can probably be de-prioritized unless a future test specifically stresses it.

## Weight: what to lighten, what to strengthen

**Lighten:**
- Observations, per the Structural section above — it's carrying more taxonomy weight than its actual reliability justifies right now.
- Resist adding more reserved tags or more memory sub-states without a specific, demonstrated need — the current six-tag governance model (`#Core #Memory #Extension #Contextual #CurrentTruth` plus the three load-policy tags) is already at a reasonable ceiling; every additional defined tag is one more thing every agent has to correctly recall the meaning of.

**Strengthen:**
- Tooling (the bulk-dump CLI feature, and possibly an optional `doctor`/audit command correlating git history against memory-route activity — already in the backlog, now doubly justified since axiom wording has a demonstrated, measured ceiling that only tooling-based approaches have broken through so far).
- An official, opt-in "sensible defaults" extension pack. Every single dogfood round needed roughly the same three directives (a language default, a safety rule, a memory-closeout rule) to get reliable baseline behavior out of a fresh install — currently every user has to write these themselves from scratch, discovering the need the same way this whole exercise did. Shipping a small, clearly-optional, `extend`-installed pack (not a Core default — that would break the "Core stays unopinionated" discipline that's working well) would let a user who wants stronger baseline reliability get it in one command instead of reinventing it.
- Explicit documentation of the directive-scope boundary (persona vs. work), since it's cheap to write and the failure mode it prevents is not obvious until you've actually watched it happen twice.

## Feature ratings

**Good — keep, low-risk, validated:**
- The core routing model itself: entrypoints, recursive categories, single marker-bounded generated regions, and concrete non-machine-local paths. Never caused a problem in four rounds of real use; patterns and crystallized decisions were both discovered reliably through pure on-demand relevance routing with zero autoload, purely from clear naming and one-line descriptions.
- Handoffs, as currently specified (post-v2 mandatory axiom). The single most reliable mechanism tested — written correctly and used correctly for cold continuation, every session, every round, once the axiom stopped being advisory.
- The Core/Memory/Extension layer discipline. The maintainers' own response to the "nothing is mandatory" finding was to strengthen a general loader axiom rather than ship opinionated Core content — the right call, and it stuck through two more rounds of testing without regressing Core's minimalism.
- `#OpenForge` scoped to Core only (post-v3). Cleanly measured fix (1,116 → 467 baseline lines), no observed downside.
- The overwrite (`.overwrite.md`) mechanism and the plain-file, git-diffable model generally — this entire multi-round investigation was only possible because every change at every layer was inspectable and diffable. That's real, demonstrated value, not just a stated principle.

**So-so — real value, but the reliability doesn't match the design intent yet:**
- The workflow/protocol primitive as a whole. The actual skill *content* is well-designed and useful when read. But getting an agent to reliably read all of it remains unsolved by wording alone (v3) and only partially solved by restructuring (v4A) or tooling (v4B) — and both of those fixes worked by making the existing self-enforcement easier, not by closing the gap outright.
- The reserved load-policy tag system generally. It's the framework's core reliability lever and it has a real, now well-measured ceiling. Not broken, but oversold relative to what it can actually guarantee (see the top finding).
- The `extend` / extension-authoring model. Solid MVP mechanics, but the shared-skill duplication problem it doesn't yet solve is a real gap, not a hypothetical one — I hit it building one extension pack redesign in a single afternoon.

**Needs rework or explicit scope-narrowing:**
- Observations, as discussed — either simplify it away or accept and document that it's aspirational rather than reliable.
- Directives governing agent communication persona/style — not a framework mechanism problem, but the framework should say plainly that this category of instruction doesn't belong in a directive, since directives elsewhere are genuinely reliable and this one class quietly isn't.

## One last note, unrelated to any of the above

Across two rounds and four independent sessions, agents flagged what looked like injected `<system-reminder>` content in tool output. I'm confident this is legitimate harness plumbing, not an actual attack — the wording matches real reminders I received directly, multiple times, in this very conversation. It's not an Open Forge problem. But it's worth recording here because every flag was handled correctly (declined, reported, not complied with) regardless of the cause, which is a small, genuinely reassuring data point about how these agents behave under uncertainty — independent of anything this framework does or doesn't do.
