# Extensions And CLI

Accepted decisions extracted from the design sessions and revised on 2026-07-20 after dogfood review.

- #Extension identifies optional packaged material added through existing Framework routes. It records provenance and composition, not higher authority. Extension is the content-agnostic installation unit, not another runtime primitive: one extension may contain a skill, workflow, directives, other routed material, a deliberate mix, or only dependencies as a convenience pack.
- Extensions add whole files inside the existing routed structure. They do not mutate shared Markdown files, install companion additions, or create another framework root.
- Extension payload routes use #Extension plus route type and scope tags by default when the file format is Open Forge-authored. Standard files such as `SKILL.md` keep their runtime-required metadata. Extension content stays relevance-routed and uses a load-policy tag only when baseline loading is deliberately chosen.
- Bundled first-party extensions live under organizational `src/extensions/{skills,workflows,packs,support}/{package-folder}/` groups. Group and folder placement aid maintenance and catalogue presentation; the manifest id owns install identity and installed payload files own runtime meaning.
- Every bundled extension declares a stable id independent of physical grouping. Manifests may also describe display metadata, versions, and bundled dependency ids. Dependency-only packs select closures without dummy runtime files. Dependency resolution is transitive, offline, dependency-first, and limited to packages already shipped with the CLI.
- A package-shaped extension keeps standalone runtime content under `payload/`. A manual install may copy that payload into the workspace and update affected generated `Entries` by hand. The CLI automates copying, indexing, dependency selection, ownership receipts, update, and removal; neither agents nor installed content require it.
- Installed routed files are complete runtime truth. Manifests, source grouping, catalogue metadata, and ownership receipts are install-time information only and must never be required to understand or use installed content.
- Normal `install` and writing `extend` commands are Git-review checkpoints. The base payload (#Core plus minimum #Memory, without optional extensions) installs first. Optional extensions require recognizable Open Forge Core anchors; inside Git those anchors must be tracked, the target scope must be clean, and planned output must be Git-visible. Outside Git, interactive use recommends initialization and needs explicit approval; non-interactive mutation stops.
- One extension invocation and its complete auto-selected dependency closure form one review unit. The CLI asks for review and commit after it; roots are installed in separate commands when separate diffs matter. Catalogue listing and dry runs are read-only and ungated.
- `extend --dry-run` previews resolved dependency order, payload effects, receipt changes, and create/update/delete/unchanged counts without writes. `extend --remove` previews or performs receipt-backed removal with the same Git checkpoint and rollback boundary.
- `--pro` bypasses only Git/Core lifecycle guards. It never bypasses dependency, manifest, containment, portable collision, link, index, preservation, ownership, or rollback safety.
- Installation preflights every resolved payload file before mutation. Paths are portable slash-separated relative paths; literal backslashes and cross-platform-invalid Windows aliases are rejected. Different bytes targeting one portable path are a blocker; identical managed payloads may share recorded owners. Bundled and local package roots reject link indirection, and managed payloads may not claim workspace-owned `.overwrite.md` files. In-process payload, index, or receipt failures roll back the whole transaction.
- Extension payloads cannot write `.git/` or `.gitignore`; repository-control changes are reviewed separately so an install cannot hide or redefine its own checkpoint.
- Every bundled package and every local source that explicitly declares a stable manifest id persists one transparent, Git-visible `open-forge.extensions.json` receipt at the workspace root. It records requested roots, dependency edges, versions, and owned payload paths and digests so update or removal can refuse modified content, protect installed dependents, and retain shared owners. Generated `Entries` bodies remain CLI-owned and may be rebuilt without invalidating entrypoint ownership.
- Idless direct local overlays and skills installed outside `extend` remain unmanaged and unclaimed. Reindexing or manually updating routing for an ordinary skill makes it visible without transferring ownership. A managed source may not silently replace an unowned path that could not be restored safely, and an unmanaged overlay may not replace a receipt-owned path.
- Removal is explicit: it removes exactly the requested installed ids and blocks while retained extensions still depend on them. Updating or removing an owned entrypoint also blocks when the final route tree would strand retained descendants. It does not infer or prune installed orphan dependencies. An owned file is removed only when its recorded content still matches.
- Shared first-party skills have one canonical skill-only extension owner; dependent workflows name both the extension dependency at install time and the concrete installed Required Route at runtime. Any complete ordinary `SKILL.md` package may coexist under `.agents/skills/`; routing it does not make Open Forge own or redefine its internals.
- Extension Markdown links resolve relative to their containing file in the assembled workspace. Same-package links resolve in isolated extension source; framework and declared-dependency links may be unresolved there but must resolve after #Core and the complete dependency closure are installed. Cross-package source stubs and duplicated payload files are not required. `doctor` and `find --follow-required` remain manifest-agnostic complete-workspace validators, so they report those intentionally absent cross-package targets when aimed directly at an isolated source payload. (revised 2026-07-20)
- External-skill interoperability is distinct-path additive, not automatic substitution for a bundled extension id. Substitution requires a future explicit satisfaction mapping or capability/ownership model.
- Registry resolution, network fetching, compatibility solving, migration hooks, automatic orphan pruning, persistent crash-recovery journaling, and remote trust policy remain outside the current contract.

The [top architecture](../documents/architecture.md#framework-composition) is authoritative for the current relationship among Core, Memory, and Extensions. The [Extensions MVP Architecture](../documents/extensions/architecture.md) expresses the complete current package model.
