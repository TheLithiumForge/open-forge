# Extensions And CLI

Accepted decisions extracted from the design sessions and idea notes on 2026-07-06.

- #Extension is optional installable material added on top of #Core and #Memory. Extension is the content-agnostic installation unit, not another runtime primitive: one extension may contain a skill, workflow, directives, other routed material, a deliberate mix, or only dependencies as a convenience pack.
- Extensions should add files into the existing routed structure instead of creating another framework root.
- Extension payload routes use #Extension plus route type and scope tags by default when the file format is Open Forge-authored. Runtime-native files such as `SKILL.md` keep native metadata. Extension content stays relevance-routed and uses a load-policy tag only when baseline loading is deliberately chosen.
- The `extend` command installs local overlays, local extension packages with `payload/`, and bundled first-party extensions.
- Bundled first-party extensions live under `src/extensions/{id}/payload` in the CLI package.
- Extension manifests may describe display metadata, versions, bundled extension dependencies, and explicit augmentations. A dependency id may reference any bundled extension shape. A local source that declares dependencies or augmentations needs a stable id so persistent dependency and ownership safety has an identity; idless plain overlays remain allowed. Dependency-only bundled packs select closures without dummy runtime files. Dependency resolution is transitive, offline, dependency-first, and limited to packages already shipped with the CLI; it never fetches from a registry or network.
- An augmentation names an existing target, an explicit target-owned slot, and a package source fragment. The installer materializes extension-owned blocks inside the already-loaded target in deterministic extension-id order. Fragments are not installed or routed separately, so augmentation adds no agent loading decision. Slots are opt-in; the installer never guesses a heading or merges unmarked prose.
- Workspace `.overwrite.md` companions remain the final local-precedence layer. Managed extensions cannot claim that singleton customization path merely to modify shared behavior.
- The bundled catalogue derives payload content labels from files. Interactive selection shows the entire catalogue, automatically marks transitive dependencies as required, locks them while needed, and releases orphaned requirements. This display and selection state never replaces installed runtime routes.
- `extend --dry-run` previews resolved order, payload and augmentation effects, receipt changes, and create/update/delete/unchanged counts without writes. `extend --remove` previews or performs receipt-backed removal with the same Git checkpoint and rollback boundary.
- Normal `install` and writing `extend` commands are Git-review checkpoints. The base payload (#Core plus minimum #Memory, without optional extensions) installs first. Optional extensions require recognizable Open Forge Core anchors; inside Git those anchors must be tracked, the target scope must be clean, and planned output must be Git-visible. Outside Git, interactive use recommends initialization and needs explicit approval; non-interactive mutation stops.
- One extension invocation and its complete auto-selected dependency closure form one review unit. The CLI asks for review and commit after it; roots are installed in separate commands when separate diffs matter. Catalogue listing and dry runs are read-only and ungated.
- `--pro` intentionally bypasses only Git/Core lifecycle guards. It never bypasses dependency, manifest, containment, portable collision, link, index, preservation, or rollback safety.
- Installation preflights every resolved source file and augmentation before mutation. Manifest and payload paths are portable slash-separated relative paths; literal backslashes and cross-platform-invalid Windows aliases are rejected. Different bytes targeting one portable path are a blocker; identical managed payloads may share recorded owners. Bundled and local package roots reject link indirection, augmentation fragments never become payload files, and managed payloads may declare only empty augmentation slots rather than pre-owned blocks. In-process payload, augmentation, index, or receipt failures roll back the whole transaction.
- Core managed, scoped-framework, and generated-index writes are also one rollback-capable operation with link/hardlink, Git-visibility, and receipt preflight. Core reinstall refuses to change a receipt-owned file or remove/alter an occupied augmentation slot; the owning extension must be updated or removed explicitly first.
- Extension payloads cannot write `.git/` or `.gitignore`; repository-control changes are reviewed separately so an install cannot hide or redefine its own checkpoint.
- Every bundled package and every local source that explicitly declares a stable manifest `id` persists one transparent, Git-visible `open-forge.extensions.json` ownership receipt at the workspace root. It records requested roots, dependency edges, versions, owned payload paths and digests, and augmentation blocks so update/removal can refuse modified content, protect installed dependents, and retain shared owners. Receipt `sha256` protects extension-authored bytes; bounded generated `Entries` bodies belong to the CLI and may change through `index` or Core without invalidating entrypoint ownership. The receipt is CLI state only: agents never need it for routing or meaning, and materialized Markdown remains complete runtime truth.
- Idless direct local overlays without dependency declarations and externally managed/APM skills remain unmanaged and unclaimed. A local overlay may opt into managed lifecycle by declaring a stable `id`; dependencies and augmentations require that identity. Reindexing direct or external skills routes them without transferring ownership. A managed source may not silently replace an unowned path that could not be restored safely, and an unmanaged overlay may not replace a receipt-owned path or invalidate a retained owned block.
- Removal is deliberately explicit: it removes exactly the requested installed ids and blocks removal while any retained extension still depends on them. Updating or removing an owned entrypoint also blocks when the final route tree would strand retained descendants; the same plan must move or remove them, or another owner must keep the route host. It does not yet infer or prune installed orphan dependencies; a future explicit, previewable prune operation needs its own root and legacy-package policy. An owned file is deleted only when its extension-authored digest still matches and no owner remains; an augmentation block is removed only when its owned content still matches. `--pro` never bypasses these ownership checks.
- Shared first-party skills have one canonical skill-only extension owner; dependent workflows name both the extension dependency at install time and the concrete installed Required Route at runtime. Native skills installed directly or by an external manager may coexist under `.agents/skills/`; reindexing routes them without taking ownership of their contents.
- External-skill interoperability is distinct-path additive, not automatic substitution for a bundled extension id. Substitution requires a future explicit satisfaction mapping or capability/ownership model; until then, local workflows reference externally owned routes directly and first-party paths keep one owner.
- Final extension design still needs richer route templates, source trust/provenance beyond local package identity, compatibility/version solving, crash-recovery journaling, registry/network policy, and richer authoring helpers. Persistent local install/update/remove ownership is now implemented through the transparent receipt.
- Installed files remain runtime truth. Manifests may help install and migrate, but agents should not need hidden manifests to route at runtime.
