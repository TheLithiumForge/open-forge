# Observation: CLI Review Rationale And Anomalies May Reveal Framework Patterns

Date: 2026-08-18. Scope: active replacement CLI implementation and its use of
Open Forge routing, Tasks, phases, agents, review, tests, and verification. This
is experimental evidence, not an accepted reusable Pattern.

## Observation

Finding-only review summaries lose useful evidence about why independent roles
converge, which alternatives recur, and which tradeoffs repeatedly decide the
result. CLI dogfooding also exposes agent, packet, workflow, projection, and tool
anomalies that can be lost when only the final successful artifact is retained.
Recording sanitized rationale and anomalies may identify improvements worth
promotion after recurrence.

## Evidence And Source

- A bounded production-structure pass materially improved locality and file
  responsibilities but left a long invocation-binding construction and kept
  CLI-wide status, exit, stream, and view policy under one command. Maintainer
  inspection identified both issues and requested a broader architectural
  assessment before the next phase.
- A fresh architecture advisor agreed that shared process presentation is
  justified by the accepted cross-command contract, while warning against a
  runtime-keyed dictionary, per-call delegate allocation, reflective generic
  rendering, and artificial context bags. The resulting synthesis retains a
  typed static table, closed AOT-safe presentation, command-local projections,
  and contexts only for real stages.
- An adversarial review role could not start because its configured execution
  profile was unavailable. The Mastermind used a separate advisory role for the
  same bounded challenge instead of treating the missing review as evidence.
- Two bounded repository explorations reached their step limit after returning
  useful but incomplete inventories. The Mastermind completed load-bearing
  authority checks through direct source inspection.
- Specialized repository search operations and a direct search executable failed
  because expected local execution prerequisites were unavailable. Direct file
  reads and bounded explorers supplied the needed evidence without changing the
  workspace.
- The specialized local configuration-guidance loader failed for the same
  unavailable execution prerequisite. Existing repository guidance and the
  runtime's explicit valid configuration-name feedback were sufficient to apply
  the smallest local correction; reinstall verification remains required.

No provider, model, AI, runtime-profile, session, task, review, handoff, or hidden
orchestration identifier; personal, user, or machine identifier; secret or token;
local absolute path; or incidental environment fingerprint is retained here.

## Conclusion, Reasoning, And Tradeoffs

The current best option is to require each review return to preserve conclusion,
reasoning, strongest alternatives, tradeoffs, and change conditions, while the
Mastermind owns sanitized persistence and post-review comparison. This keeps
fresh reviews independent and avoids forcing read-only reviewers to mutate
Memory.

The alternative of showing every reviewer prior conclusions would make
comparison easier but would anchor the review and weaken evidence of independent
convergence. Creating one Observation per review would retain detail but produce
fragmentation and poor recurrence tracking. The chosen approach appends to one
matching Observation only when scope and meaning align.

## Scope

This evidence currently applies to Open Forge's own CLI implementation and agent
workflow dogfooding. It does not yet prove that every installed workspace needs
the same default Directive or that review rationale should become a reusable
Pattern.

## Uncertainty

The first architecture comparison is not enough to establish recurring reviewer
behavior. Some anomalies may be local configuration or bounded-packet sizing
issues rather than Framework defects. Future occurrences must distinguish those
causes.

## Relevance

The record can reveal repeated reviewer ideas, recurring agent failure modes,
packet-quality problems, and maintainer corrections that should refine Framework
guidance, roles, workflows, or implementation rather than being rediscovered in
later CLI Tasks.

## Occurrences

- Initial occurrence: the architecture advisor and maintainer independently
  favored centralized shared process policy and cohesive call inputs, while the
  advisor supplied narrower guardrails against speculative abstraction.
- First governance review comparison: independent semantic and writing reviews
  both accepted the direction but required alignment before acceptance. They
  converged on the narrow Purple exception, one canonical sanitization boundary,
  removal of duplicated role instructions, and deferring installable Framework
  promotion. The semantic lens additionally identified broad shell authority on
  two read-only roles, an unmodeled post-Blue activity, insufficient clean-packet
  isolation, and incomplete advisor/council return projection. The strongest
  alternative was to rely on Mastermind packet discipline alone; explicit role
  and lifecycle rules were preferred because standalone execution must remain
  safe and auditable. The accepted tradeoff is limited wording repetition for
  independent role completeness.
- Correction rereview: both lenses passed and independently concluded that the
  authority, lifecycle, role, template, and privacy projections now agree. Both
  identified the same strongest alternative—remove repeated standalone wording
  and rely on inherited directives—and rejected it because independent roles and
  copy-ready templates must preserve the boundary without hidden context. The
  change condition is also shared: any future sanitization-boundary change must
  update the canonical Directive and standalone projections together.
- Closed implementation occurrence: the implementation role followed the detailed
  architecture packet, reduced all five targeted behavioral call surfaces, kept
  genuine data records intact, and preserved the complete focused and managed
  evidence. One intermediate missing namespace import was corrected before the
  final verification sequence. This supports complete decided packets while
  preserving Mastermind inspection and independent review.
- Code-review comparison: the improvement lens found no material local change;
  repeated topology-result initializers and small policy convenience methods were
  not enough to justify another abstraction. The correctness lens reached its
  bounded step limit after inspecting the full diff, then resumed as the same lens
  for only JSON and process-presentation synthesis and passed. It found concrete
  source-generated JSON, exhaustive guarded disposition, single-strategy
  selection, and preserved process paths sufficient. Its strongest counterpoint
  was missing dedicated isolation for unknown enum rejection, delegate allocation,
  and every process status. Both lenses favored no additional change absent a
  measured allocation issue, new command consumer, changed output, or concrete
  regression.
- Maintainer follow-up: the first implementation increment centralized status and
  presentation policy but still left global signals, bound flag values,
  invocation state, adjacent result shapes, renderer selection, output, and
  completion embedded in route-list composition. The maintainer required the
  missing shared shell architecture and independently testable messages before
  Purple. This narrows the earlier “no material improvement” conclusion: it was
  valid for the assigned local diff but its packet did not ask whether the first
  command had completed the intended project-wide shell.
- Shared-shell boundary comparison: a bounded authority exploration and a cold
  advisory challenge agreed that the accepted contracts support global status,
  flags, terminal, presentation, workspace, envelope shapes, streams, exits, and
  typed shell messages while route semantics and mutation recovery stay local.
  They converged on terminal validation before help/version bypass, no forced
  workspace, concrete invalid-input conversion, explicit writer injection,
  directly callable stages, operation-at-most-once, unknown-value tests, and no
  generic rollback. The
  strongest smaller alternative is the existing presenter-only boundary; it was
  rejected because future commands would duplicate global invocation and stage
  infrastructure.
- Deployment recurrence: after the local adversarial-role source was corrected,
  the active runtime still attempted to use its stale unavailable execution
  configuration. A separate advisory role completed the bounded challenge. This
  suggests source edits require explicit reinstall or runtime reload evidence
  before the corrected role is considered available.
- Shared-shell governance review: independent semantic and writing lenses both
  required narrower wording before implementation. They converged on terminal
  validation before short-circuiting, preserving non-invalid boundary statuses,
  explicit primary-result versus diagnostic output, direct evidence for every
  shell stage, one exact `command plug-in` definition, and rollback language that
  does not imply all effects are reversible. The semantic lens additionally
  required `workspace: null` for accepted no-workspace result envelopes and a
  shell-specific dependency-injection prohibition. Its bounded steps ended after
  findings without a complete rationale record, so a targeted correction
  rereview remained required before accepting the governance packet.
- Shared-shell governance rereview: the semantic lens passed after all boundaries
  aligned and identified a presenter-only shell as the strongest smaller but
  insufficient alternative. The writing lens required two final Task phrases to
  reserve the concrete `CliCommandPipeline` name and explicitly preserve reverse
  recovery, compensation, or no reversal as command-local choices, then passed.
  Its final return omitted the required rationale block despite an explicit
  packet instruction; the Mastermind retained its stated evidence and conclusion
  but records the return-shape miss for future role refinement.
- Parser-ownership correction: maintainer inspection found that the attempted
  shared shell still rescanned raw arguments, duplicated option spellings and
  occurrence logic, and retained a command/Foundation YAML-context workaround.
  Exact pinned-library source research then showed that parser arity already
  rejects repeated scalar value tokens, occurrence counts remain available on
  typed option results, and repeated bare Boolean flags are idempotent. Only the
  accepted delimiter distinction lacks a sufficient public parser fact. The
  selected correction gives parser semantics to the parser and limits lexical
  inspection to that one bounded job. The strongest alternative—keep both paths
  because tests passed—was rejected because dual parsing creates drift and makes
  the CLI harder to inspect.
- Deliberate-rebuild correction: a cancelled implementation correction left a
  partially modified, unverified worktree after an earlier green run. Rather than
  continue local edits, the maintainer authorized disposal of the uncommitted
  experiment and required a reviewed global foundation before route behavior is
  reintroduced. This is stronger evidence that passing counts do not accept the
  wrong structure and that cancellation requires fresh verification before any
  reported result can be reused.
- Global-foundation review recurrence: the first focused correctness and
  improvement reviews both found that green tests did not yet prove fail-closed
  direct stages, one version owner, or cross-platform newline evidence. After
  correction, rereview found the deeper ordering issue that an independently
  callable stage could invoke an operation, renderer, or writer before rejecting
  a malformed finite value. Final correction validates before every side-effect
  boundary, and both lenses then passed. The strongest alternative was to trust
  only messages created by the immediately preceding stage; reviewers rejected it
  because the architecture deliberately permits direct stage entry for tests and
  debugging. Repeated constant-time validation is the accepted cost.
- Capability-boundary occurrence: the implementation role completed managed
  verification but could not execute locally restricted publication commands.
  The Mastermind ran the accepted Native AOT boundary instead of weakening the
  evidence requirement. This supports explicit takeover when a role's authority,
  rather than the implementation, blocks required verification.
- Verification-order occurrence: running production and `SystemTests` Native AOT
  publication concurrently made both builds write the shared production output
  and emitted a transient retry warning. The warning-bearing run was rejected as
  clean evidence; sequential publication passed without warnings. This occurrence
  indicates that these two publication commands should run sequentially when they
  share the production build, even though their final output folders differ.
- Route safety-review recurrence: complete retained behavior counts, warning-free
  build, and built-process evidence did not expose physical directory cycles,
  unsafe fallback facts, exact-path exceptions, or read-failure status collapse.
  A fresh correctness lens found those boundaries by following filesystem and
  direct-input failure paths rather than sampling expected rows. Correction added
  physical-identity tracking before enumeration, null rather than guessed
  workspace facts, typed invalid exact paths, and distinct safety/read policy.
  Focused rereview then passed. The strongest alternative was to declare symlink
  traversal unsupported, but no accepted contract established that exception.
- Route local-improvement recurrence: the improvement lens found dead graph and
  absolute-path state, repeated sort and ambiguity work, duplicate canonical
  entrypoint recognition, unused wire definitions, weak focused assertions, and
  one YAML deserializer construction per source. The accepted correction removed
  the dead work, centralized identities, strengthened exact evidence, and reused
  one operation-local deserializer. A process-global cache was rejected because it
  would add an unnecessary concurrency assumption for marginal reuse.
- Purple evidence recurrence: the first test-topology reviews found that shared
  temporary-workspace cleanup relied on path shape rather than positive ownership,
  process cancellation did not completely drain redirected streams, and the
  workflow repeated the authored executable version. Correction added an
  ownership marker and random token, replacement and mismatch refusal,
  deterministic marker-free snapshots, cancellation kill/wait/drain behavior,
  and one MSBuild-derived version passed to managed and published EndToEnd
  evidence. The strongest smaller alternative was to keep project-local helpers
  and a fixed expected version. It was rejected because Integration and EndToEnd
  now have identical real-OS workspace semantics and the executable already has
  one authored version source. The tradeoff is a larger cohesive safety helper
  rather than duplicated short helpers with weaker ownership guarantees.
- Review-role return anomaly: fresh correctness, improvement, alternate review,
  and precautionary implementation-role invocations completed without a usable
  return, and the implementation invocation changed no file. The Mastermind
  inspected the exact Purple paths, three-project references, shared support,
  workflow, managed runs, sequential Native AOT publications, published test
  executions, audit, old-reference scans, and diff checks directly. This fallback
  does not count as independent review evidence. The strongest alternative was to
  pause a verified phase solely for another role retry. The selected tradeoff is
  to preserve the anomaly and keep a fresh whole-Task review pending. A repeated
  empty return in a later Task would justify investigating role-result transport
  before relying on optional review orchestration.
- Maintainer-supplied review recovery: a later detailed static architecture and
  implementation review, modern .NET and explicit-`Shared` addendum, and scoped
  route-model correction supplied usable independent evidence. The review found
  blocking route-list acceptance gaps despite the first public and full local
  gates, judged the implementation a viable base for continuation rather than
  final acceptance, and authorized a complete Task refinement. Expected passing
  process evidence did not expose the observed selection-shape, containment,
  diagnostics, help, cancellation, read-cause, human-parity, and evidence gaps.
  The strongest alternative was to accept the passed gates and defer those gaps
  to later commands; it was rejected because the first retained command must
  establish the shared shell and safety baseline. The selected tradeoff is a
  broader current Task with frozen public syntax instead of either a rewrite or
  partial acceptance. This removes the earlier absence of independent whole-Task
  evidence but does not erase the helper result-transport anomaly. The conclusion
  changes only after repeated affected and full evidence plus a fresh report show
  no blocking finding. A review invocation without an actual report remains no
  evidence.
- Refinement-Gray review comparison: the correctness lens passed the unwired
  diagnostic, selection, read, and containment shapes. The improvement lens first
  blocked on convention-only selection construction, a duplicate-looking
  diagnostic message, and ambiguous final-path naming. The implementation adopted
  `ResolvedSource` and `ResolvedPhysicalPath`. Mastermind kept direct legacy
  constructors until Green because changing their current invalid-result behavior
  would violate Gray, and kept a nominal diagnostic message because diagnostic
  and primary renderer call surfaces have distinct contracts. Focused rereview
  then passed. The strongest alternative was to close all selection construction
  during Gray; it reduces bypass risk but crosses the frozen no-behavior boundary.
  The selected tradeoff is temporary constructor duplication with a blocking
  Green scan for any bypass. Expected existing EndToEnd evidence initially failed
  because the invocation omitted its required built-CLI environment; the run was
  rejected as harness setup, and the correctly configured run passed all cases.
  The conclusion changes if Green leaves a bypass, merges diagnostic and primary
  contracts, or uses resolved-path facts inconsistently.

## Follow-Up And Promotion Signals

For each comparable review or anomaly, append:

- bounded role and review scope;
- conclusion and decisive reasoning;
- strongest alternative and material tradeoff;
- agreement or disagreement with earlier occurrences, compared only after the
  independent pass;
- expected versus observed agent, workflow, command, or tool behavior;
- consequence, recovery, and whether Mastermind takeover was needed; and
- the smallest rule, Pattern, role, workflow, or implementation change suggested
  by recurrence.

Propose promotion only after multiple independent occurrences show stable meaning
and useful scope. Preserve counterexamples. Reject or narrow the hypothesis when
records show that prior conclusions merely anchored later reviewers or that the
capture cost exceeds its refinement value.
