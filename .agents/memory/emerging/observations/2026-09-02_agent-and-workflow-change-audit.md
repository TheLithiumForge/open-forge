## Conclusion, Reasoning, And Tradeoffs

### 1. Role additions and responsibility changes

- **Overseer:** `5aad04ac` grants the `review-mastermind` route and makes it a
  read-only validator/router for bounded immutable snapshots. It also carries
  topic budgets, canonical evidence, C# packet requirements, quiet-child
  handling, and runtime-derived capacity. `3356eba1` adds permanent task IDs,
  queue/grace rendering, and Task-record progress identity. `412a707f` adds
  the streamlined assured profile. `996c2e17` adds literal Luna/max support
  packets while preserving semantic ownership.
- **Task Mastermind:** gains the same review route, task-local budget authority,
  immutable snapshot and receipt requirements, writer-only finding dispositions,
  and permanent-status derivation. In the streamlined profile it keeps
  Preflight plus explicit Gray/Red, assigns one Brilliant Implementer through
  Green and verification, then performs one fresh holistic review covering
  behavior, production structure, and test/evidence quality before one grouped
  improvement pass. Luna/max support remains bounded and non-semantic.
- **Integration Mastermind:** gains immutable ancestor/candidate/parent-tree
  lineage checks, formerly-untracked-artifact checks, quiet-agent and explicit
  ownership-transfer handling, and the four-line checkpoint. It explicitly
  does not own review topics or spawn Review Mastermind; it consumes reviewed
  task commits and preserves their inspected identities.
- **Review Mastermind (new):** is a read-only coordinator. It validates each
  snapshot's task mapping, freshness, phase/milestone status, receipt, Git
  lineage, and topic budget; routes only the four standing topics; joins by
  snapshot and original writer; and preserves duplicates/dissent. It cannot
  disposition findings, repair files, change task state, or synthesize a fifth
  topic.
- **Topic reviewers (new):** `architecture-ownership-refactoring`,
  `behavior-contracts`, `csharp-conformance`, and `test-evidence` are separate
  read-only, object-only roles. Their permissions allow only
  `inspect-git-objects`; they do not use Bash, native filesystem/LSP state,
  edit, commit, or decide architecture/product/acceptance. The C# topic and
  any other topic that inspects C# must independently read the complete three
  current C# Directive files.
- **Brilliant Implementer:** no role-file addition was proven in the horizon.
  The streamlined Workflow assigns the existing role the coherent Green,
  focused verification, and grouped post-review improvement boundary. This is
  additive workflow selection with an explicit exception for material
  Preflight-named Blue/Purple protection, not a replacement of its role.

### 2. Rule and workflow changes

- **Assured/streamlined development:** Preflight, Gray, and Red stay explicit;
  one Brilliant Implementer owns Green through focused verification and repair;
  Task Mastermind's one fresh whole-task review absorbs ordinary Blue/Purple
  assessment. Separate Blue/Purple owners return only for a material risk named
  by Preflight. The CLI ledger records Tasks 4–6 as the comparison treatment,
  with critical-path time, handoffs, correction cycles, dispositioned findings,
  gate failures, integration friction, and post-acceptance misses as success
  measures. This is not yet proven or universal.
- **Review orchestration:** ordinary review still uses the accepted baseline
  plus the explicit current changed/untracked target. The coordinated path is
  opt-in, one active wave per immutable task snapshot, one stable budget unit
  per selected topic, coordinator validation/synthesis at zero units, and
  advisory topic results that never replace a required fresh holistic review.
  The original writer revalidates findings, chooses dispositions, owns repair,
  and changes task state.
- **Immutable-object review:** the fixed local engine supports eight named
  operations (`object-type`, `object-content`, `tree-list`, `tree-path`,
  `changed-paths`, `diff`, `diff-check`, `is-ancestor`). It accepts complete
  40/64-character object IDs and explicit safe repository-relative paths only;
  rejects refs, selectors, ranges, options, unsafe paths, and unknown fields;
  disables lazy fetches and bounds output. The OpenCode adapter is structured
  and shell-free. Review records bind ancestor/candidate/parent/authority
  commits and trees, and all relevant formerly untracked artifacts must be
  committed. Non-identical runtimes receive bounded immutable content or a
  review gap.
- **Progress and task IDs:** the project ledger owns one permanent numeric ID
  and actual name per top-level task, with no reuse. A Task record owns the
  accepted phase/milestone horizon, current phase ordinal, completed milestone
  count, and state suffix. A stable `/Y` total is shown only if the ledger
  declares one; queue size is not a denominator. Active, Recently completed,
  and Queued sections derive from those sources; completion remains visible for
  exactly two later progress-bearing Overseer updates.
- **Caveman checkpoints:** Task, Integration, and Review Mastermind returns use
  exactly:

  ```text
  Done: <completed evidence or commit>
  Now: Task X[/Y] “<actual task name>” (phase A/B): milestone C/D — <active operation>
  Next: <next meaningful milestone>
  Blocker: <none or one real blocker>
  ```

- **Quiet-agent handling:** missing optional child detail is `progress
unobserved`, not health/failure evidence. Inspect exposed runtime state,
  owned processes, Git state, and artifacts; do not cancel, duplicate, or take
  over on silence. Transfer a mutable boundary only after confirmed
  interruption, stopped owned mutators, inspected partial artifacts/evidence,
  and an explicit ownership transfer. Capacity comes from runtime evidence,
  not a historical hard-coded cap.
- **Commit policy:** where authorized, make a coherent green commit that
  improves review, recovery, or integration; do not create per-file,
  keystroke, or formal-phase ceremony. A coordinated review commit is an
  immutable snapshot and must include relevant formerly untracked artifacts.
  The active trial also requires a natural past-tense subject; integration and
  final acceptance remain separate authority boundaries.
- **C# design-file enforcement:** every direct C# author/reviewer packet must
  require independent reading of the complete current
  `.agents/directives/csharp/_csharp.md`, `design.md`, and `style.md`, without
  hard-coded hashes. Separately, `design.md` and the Pattern require every
  named enum mapping plus a discard arm throwing `ArgumentOutOfRangeException`,
  with tests for named mappings and one undefined runtime value; no analyzer,
  generator, reflection, union, or warning suppression is justified for this
  boundary alone.
- **Luna/max delegation:** `996c2e17` expands use for disjoint menial/simple
  work, exact shell/build/test/AOT execution, artifact inspection, and
  large-output summarization. Packets are literal and bounded; support workers
  cannot choose commands, infer product/architecture/test meaning, edit, or
  mutate the same live boundary concurrently. The `AGENTS.md` exception can
  skip context only for an explicitly labelled eligible no-context mechanical
  task; semantic analysis, investigation, design, implementation, integration,
  and correctness review always load normal Open Forge context. `Sol/xhigh`
  remains for consequential design/implementation/integration/fresh review.

### 3. Ideas, authority, replacements, and placement

The user idea was not promoted wholesale. `continuous-targeted-review-
orchestration.md` remains an Emerging Idea and explicitly says it does not
authorize continuous review in every task. `review-orchestration-trial-
controls.md` records the selected bounded experiment, trial evidence, and open
questions; it explicitly says trial evidence is not new binding policy. The
smallest general controls (immutable intake, topic boundaries, writer
disposition, receipts, quiet handling, and progress semantics) were promoted
into active Directives, Workflows, templates, and role files. Automatic
per-file review, a fifth topic, dirty/untracked snapshots, fixed concurrency,
cross-runtime enforcement/collection, reviewer economics, and Extension
packaging were not promoted.

No accidental additive-to-replacement change is proven. The exact current
rules preserve the prior paths: `review.md` has ordinary and coordinated
branches; the streamlined profile restores separate Blue/Purple owners when
Preflight names material risk; semantic work still loads normal context; and
the Review Mastermind cannot change writer or task ownership. The observed
replacement-like changes are deliberate and bounded: `3356eba1` replaces
queue-position display with permanent identity/ledger state; `412a707f` folds
ordinary Blue/Purple assessment only inside the selected Tasks 4–6 profile;
the review coordinator's early candidate disposition concept was narrowed to
linking duplicates/preserving dissent while the writer disposes; and
`234199d5` deliberately removes automatic mutation rollback/restore. These are
recorded policy corrections, not evidence of an idea silently replacing a
universal behavior.

For root scripts, `scripts/inspect-git-objects.ts` is the fixed read-only Git
engine introduced by `5aad04ac`; `.opencode/tools/inspect-git-objects.ts`
imports it, and `scripts/inspect-git-objects.test.ts` exercises all operations,
limits, no-lazy-fetch behavior, adapter shape, role permissions, and ignore
rules. No package script directly names these two review scripts, but the
adapter and test are concrete consumers. The engine's root placement is
questionable only as a future packaging decision: `src/extensions/orchestration/README.md`
explicitly keeps the extension planning-only for now and says to retain these
sources for local validation until extraction is validated. They are not
orphaned. Separately, `scripts/patch-codex-agent-models.ts` predates the audit
window (last changed in `d3beb3be`) and is consumed by `package.json`'s
`apm:install`; it reads authored `.apm/agents` frontmatter and patches generated
`.codex/agents` model fields, with `--check` verification. It is not the
immutable Git inspection tool and is not orphaned.

## Scope

This record covers tracked agent sources, orchestration/review/development/C#
Directives, Workflows, the selected Emerging Ideas, execution-rule continuity,
package scripts, generated-runtime mapping, the review engine/adapter, and the
current extension planning boundary in the stated Git horizon. It does not

## Uncertainty

The classifications distinguish authored source from generated projection and
current policy from candidate trial material. The review and streamlined lanes
are implemented and locally evidenced, but their comparative quality,
latency, and reviewer-economics outcomes are not yet established. The lockfile's
`generated_at` value is older than the audited commits, but the retained trial
evidence explicitly rejected a stale-lock conclusion after frozen generation;
the timestamp alone is not evidence of debris. Runtime closure, collection
acknowledgement, capacity refusal, cross-runtime permission parity, and hot
role reload remain unverified. No claim is made that a package or generated
projection is an authority source.

## Relevance

The audit prevents maintainers from reconstructing several days of role and
workflow history from commit graphs, while preserving the crucial boundaries:
the review trial is opt-in, the writer still owns dispositions, immutable
lineage is not mutable workspace state, Luna/max does not acquire semantic
authority, and the streamlined lane is a measured treatment rather than a
universal phase deletion.
