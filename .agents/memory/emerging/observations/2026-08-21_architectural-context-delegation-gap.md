# Architectural Context Was Missing From Bounded CLI Delegation

## Observation

The replacement CLI used a high-context primary agent with bounded implementation
roles, but the arrangement did not produce a coherent architecture efficiently.
The primary context had a detailed external review and a broad active Task, while
the implementation role saw one oversized behavior packet whose sequence deferred
the accepted structural foundation. The role completed its assigned slice, but
the result optimized the old structure and left a system-level safety gap.

This occurrence suggests that bounded implementation roles work well for a
feature or small closed Task, but not for unresolved architecture. A high-context
primary agent cannot compensate after delegation for architecture, system needs,
strict boundaries, and integration detail that were absent from the packet.

## Evidence And Source

- The accepted CLI review required a process-wide `Shared` boundary, command-local
  `Shared/<Capability>` support, direct solution membership, centralized build
  artifacts, and component-wise physical containment.
- The active Task ordered behavior Green before the structure increment. The
  implementation packet explicitly prohibited the later structural work, so the
  implementation expanded the obsolete physical layout rather than the accepted
  target layout.
- One implementation increment changed 24 files with 1,224 insertions and 254
  deletions. Its physical-containment class reached 446 lines.
- Existing focused evidence passed, but one additional real-filesystem case showed
  that a link chain could leave the selected workspace and re-enter it. The result
  was `complete` where the accepted contract required `blocked`.
- The maintainer stopped implementation, preserved the result only as WIP
  evidence, and directed a greenfield architecture, Plan, and detailed Task
  hierarchy before feature implementation resumes.

The evidence is repository-relative and retains no provider, model, runtime,
session, personal, machine, or hidden orchestration identifier.

## Conclusion, Reasoning, And Tradeoffs

The current multi-agent development arrangement is not reliable for architecture
when a bounded implementer receives only its local slice. The primary architecture
agent must first settle the complete system model, implement cross-cutting
foundations and callable contracts, and turn the remainder into closed Tasks with
strict references, boundaries, consumers, evidence, and stop conditions.

The strongest alternative is to give each implementation role the complete
review and ask it to discover the best architecture independently. That may expose
useful alternatives, but it repeats expensive discovery, distributes architecture
authority, and makes integration depend on reconciling several local designs.
The accepted tradeoff is more deliberate work in the primary context before
delegation, followed by cheaper bounded implementation and review.

## Scope

This occurrence applies to the replacement CLI and similar greenfield or
cross-cutting programs. It does not show that bounded implementation roles are
ineffective for small features, mechanical work, or Tasks whose architecture and
contracts are already closed.

## Uncertainty

One reset does not prove that every multi-agent architecture effort fails. Packet
size, phase ordering, and the unresolved physical-containment algorithm all
contributed. The next CLI foundation and Task hierarchy should test whether
explicit top-down and task-master perspectives remove those causes.

## Relevance

Without this record, later work may repeat the same pattern: retain a broad review
in the primary context, send a locally detailed but architecturally incomplete
packet, accept passing local evidence, and discover the integration error only
after substantial implementation.

## Occurrences

- Initial occurrence: the route-list refinement implemented behavior in a layout
  already scheduled for replacement and missed an intermediate physical escape
  that the broader contract prohibited.

## Follow-Up And Promotion Signals

- Use the top-down architect and task-master perspectives for the replacement CLI
  foundation and first complete command.
- Compare implementation rediscovery, correction rounds, architecture defects,
  and integration findings with the preserved WIP increment.
- If the approach succeeds across several Tasks, promote the smallest useful
  packet requirements or perspective shape. If it adds ceremony without reducing
  rework, narrow or reject it.
