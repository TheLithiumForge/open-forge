# Supervised Luna Preparation Trial Results

## Scope

This Observation records two opt-in preparation samples. It does not replace
the ordinary Task Mastermind, authorize Luna/max semantic implementation, or
change the default development Workflow. The selected workflow remains
[Supervised Luna Preparation Trial](../../../workflows/supervised-luna-preparation-trial.md).

## Sample 1: Task 13 Native CI Preparation

Task 13 produced a useful bounded preparation record. Candidate
`e76896965e1cce51b7295f899499c5a7d0cce252`, tree
`c204c17b4bdda87bf43a479879d6ebcf87472283`, changed only the Task 13 record
relative to its direct parent. Integration `203e6840974af7df3fe677b3d3db625c2455d2a2`,
tree `1fbd90b4007ec9149e90e09a60825f5c78b4fc25`, converged its phase 1/3,
milestone 2/6 handback with current project control.

The preparation separated Linux execution from the accepted future
Linux/macOS/Windows x64 package horizon, kept ARM undecided, protected CI,
packages, executable source, tests, contracts, and release authority, and passed
one Sol/xhigh review with one grouped correction. It materially reduced later
inventory work and supplied exact revalidation triggers.

This is not clean Luna-only evidence. A requested Luna child runtime was
unavailable and a fallback result contributed to the preparation. The useful
outcome supports the supervised preparation shape, but it does not establish
that a Luna-only Task Mastermind team is reliable or cheaper.

## Sample 2: Task 14 Extension Install Preparation

Task 14 selected a read-only Luna/max preparation against clean baseline
`de40d550c00e51f55fe7e8b5d39297c450f721e9`, tree
`e6040c4996eb8af5375979b54a9bafc198438a34`. The lane received a closed packet,
normal Open Forge loading, a three-child maximum, explicit C# Directive reads,
protected paths, and a compact return contract.

The lane returned no checkpoint or preparation packet across repeated
supervision intervals. An interrupt followed by an exact return-now packet also
produced no result. The Overseer terminated the sample. No file, Git, Task,
production, test, contract, or architecture state changed, and no partial result
is accepted. Task 14 remains unprepared and will receive a fresh Sol/xhigh
activation after Task 12.

This is a latency and observability failure of the experiment, not evidence that
Task 14 is blocked or that the agent produced incorrect semantic work. Token,
child, handoff, finding, and revalidation measurements are unavailable because
the lane returned no receipt. The observed critical-path cost was supervisory
waiting plus one interrupt and one unproductive follow-up.

## Current Disposition

- Keep Luna/max workers for exact shell/build/test execution, artifact
  inspection, simple mechanical changes, and large-output summarization.
- Keep semantic C#, architecture, lifecycle, recovery, public wire, and test
  meaning under Sol/xhigh ownership.
- Allow another Luna/max preparation Mastermind only when the result is smaller
  than Task 14's cross-cutting lifecycle inventory and has an explicit early
  checkpoint.
- End a preparation trial after two explicit checkpoint or return requests go
  unanswered across separate supervision intervals. Record the trial as
  uneconomic or unobservable without calling the Task failed.
- Do not treat either sample as enough evidence to change the default Workflow.

The next useful comparison is a narrow, closed, derivative preparation with a
small durable result, measured against an equivalent Sol/xhigh preparation. Do
not repeat Task 14's broad read-only inventory merely to collect another sample.
