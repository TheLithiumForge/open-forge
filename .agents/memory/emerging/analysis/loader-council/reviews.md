# Loader Council Reviews

Stage 2 output, unchanged except for removed local paths and runtime labels. Reviewers saw proposals only as letters and did not rank their own. The [record](record.md) holds the aggregate ranking.

## Prosecutor (Proposal D)

#### Critiques

Reliability improvements remain unproven across the peer proposals. I favor designs that specify how mandatory sources become reachable, while accounting for manual use, customization, and migration.

**Proposal A.** Checked replacements are its strongest contribution because an outdated customization produces a detectable mismatch. However, “These tags never activate an unselected parent” preserves discretionary discovery of mandatory rules. Tag expansions and changed updater behavior also enlarge the implementation before resolving that central problem.

**Proposal B.** B combines direct documentation access, optional catalogs, source-local conditions, and removal of catalog inheritance coherently. Its required discovery chains can make file-specific rules reachable without discretionary branch selection. The serious ambiguity is “Follow the agent tool’s instruction precedence,” which does not fully specify how native instructions combine with selected document rules across different hosts.

**Proposal C.** The `When`, `Read`, and `Use` table makes required reading and the intended use of each source unusually inspectable. However, “Read each source’s explicit required links” preserves mandatory dependencies outside the parsed table. The additional `task:` conditions and “include plausible matches” instruction also retain substantial judgment inside required selection.

**Proposal E.** E gives instructions concrete moments of use and separates refresh from candidate capture sensibly. “Compare every other visible description” is still a mental procedure without a dependable completion test. It retains hidden-parent discovery, inherited conditions, and much eager catalog reading, so its stronger wording carries more of the improvement claim than a changed mechanism does.

**Proposal F.** The drop-in directory offers the cleanest independent component lifecycle because packages can contribute separate read lists without editing one central registry. Its loading procedure is concrete, manually executable, and directly supports existing documentation. Its serious cost is aggressive rereading, with every required source refreshed at several boundaries and all conditional sources read while paths are unknown.

**Proposal G.** G offers the best balance of smaller startup, parser compatibility, and a checkable required-discovery invariant. Requiring every catalog in a mandatory file-specific branch to carry LoadNow gives a structural validator something concrete to inspect. Its remaining weakness is substantial ancestry machinery, including inherited conditions and rules, which limits how independently a leaf document can explain its obligations.

**Proposal H.** H specifies the computed result particularly well through verbatim effective bodies, source paths, selection reasons, and incomplete results for unavailable context. Its independent metadata inventory also closes the hidden-parent gap. The serious flaw is the manual fallback, which reads every LoadNow body without path filtering even when working paths are known, making large workspaces practically dependent on the CLI.

**Proposal I.** I presents a complete small startup payload, rather than counting only its loader, and directly registers mandatory rules. The shipped singleton “Active checkpoint” lacks a clear workstream-selection rule, creating a risk that unrelated sessions read or replace one another’s continuation state. Removing overlays and changing Update behavior also require substantial delivery work despite the compact Markdown.

**Proposal J.** J has the clearest staged delivery plan, separating an immediate payload reduction from broader documentation routing. However, “Neither selects an unopened branch” leaves the known mandatory-discovery problem without G’s required-path invariant. Ancestry, inherited conditions, refresh passes, status tags, and semantic overwrites remain, so the bookkeeping burden stays substantial.

#### Steal list

- **Proposal G:** Validate an uninterrupted required-read path to every mandatory file-specific source, because required discovery needs an inspectable structural guarantee.
- **Proposal A:** Use exact expected text and a unique target for managed-source replacements, because stale customizations must produce a visible conflict.
- **Proposal F:** Allow independently enabled read-list drop-ins, because component installation and removal should not require coordinating edits to one shared registry.
- **Proposal B:** Admit directly linked ordinary documents without intermediate catalogs or compulsory frontmatter, because blending must preserve the documents people already maintain.
- **Proposal H:** Return effective source bodies with paths and selection reasons, because retrieval should be reproducible and auditable without pretending to prove comprehension.

#### Most dangerous idea

H’s manual fallback says, “Read every file tagged `LoadNow`, without filtering by `applyTo`.”

In a large blended workspace, this expands prompt cost to the entire registered required inventory even when working paths are known. It also exposes the model to more mutually inapplicable instructions and makes efficient operation depend on the CLI. Manual readers should use the same matching contract as the computed path.

#### Convergence

- Turn the loader into a short operating procedure.
- Load the CLI Skill when using it.
- Move authoring and package-maintenance detail out of startup.
- Remove the inherited-marker ceremony.
- Let ordinary documentation participate at its existing location.
- Keep navigation separate from document authority.
- Preserve acceptance distinctions without treating tags or storage locations as proof.
- Keep native Skills under their runtime’s control.
- Make optional components removable without restoring them automatically.
- Judge reliability through retrieval traces and resulting behavior.
- Use explicit migration for changed loading semantics.

#### Open conflicts

1. **Required catalog paths or direct registrations.**  
   B and G preserve required discovery chains. C, F, and I register required destinations directly. I recommend shipping the required-path invariant first, with validation, because it can improve discovery using the existing representation. Benchmark direct registrations against it before accepting their larger migration and inventory costs.

2. **Checked patches or complete replacement sources.**  
   A checks targeted text replacements. F, H, and I favor complete replacement sources or explicit destination substitution. I recommend checked patches for small adjustments to managed defaults, with complete replacements available when users deliberately adopt responsibility for the whole source. Neither mechanism eliminates the need to review surrounding upstream changes.

3. **Equivalent manual selection or a conservative manual superset.**  
   Most proposals retain matching in manual use. H deliberately reads a larger set. I recommend equivalent matching when paths are known, with an explicit pending state while they are unknown. A larger fallback should require evidence that its attention cost and incorrect-application risk are acceptable.

#### Revised position

I would separate the immediate startup reduction from the larger loading-model redesign. G shows that mandatory file-specific discovery can become a structural invariant without first abolishing ancestry, relocating conditions, and changing Index ownership of Entries.

I would therefore test validated required paths against direct registrations before choosing the final representation. The experiment needs a heavily grown workspace as well as a small fixture, because flat inventories and recursive chains incur different scaling costs.

If direct registrations win, I would adopt F’s independent drop-ins instead of requiring one central manifest. I would also preserve one authoritative condition declaration and avoid making a broad updater-policy change a prerequisite for loader simplification.

For customization, I would adopt A’s checked replacement mechanism as a separately delivered capability. For evidence, I would use H’s source paths and selection reasons, backed by actual retrieval traces. Handwritten receipts would become optional, while missing sources, pending conditions, and unresolved conflicts would still require explicit reports.

## Demolitionist (Proposal I)

#### Critiques

**Proposal A.** Checked replacements are a strong contribution because an upstream change can invalidate an exception visibly instead of leaving the model to invent a merge. Optional Memory organization also improves independence. However, mandatory discovery still depends on selecting parents, while tag aliases add another language without closing that gap. The replacement machinery belongs in optional maintenance tooling rather than the reading kernel.

**Proposal B.** Removing catalog inheritance and keeping a source’s meaning independent of its incoming links makes documents easier to reuse. Its treatment of native Skills and metadata-free reference documents is also practical. The weak point is “follow the agent tool’s instruction precedence,” which needs a precise account of how native instructions interact with catalog-selected rules. Otherwise, the same workspace can behave differently across hosts without an obvious explanation.

**Proposal C.** The reading table makes required context inspectable, and its separate `Use` column correctly distinguishes compulsory reading from instruction authority. Direct links to existing human documents are especially clear. Its main cost is introducing a new policy language with three condition types and three uses. Task predicates retain semantic judgment, so that added grammar needs evidence that ordinary file conditions and explicit instructions cannot cover the common cases.

**Proposal D.** This proposal gives the strongest account of missing context, pending conditions and reading rules before investigating file bodies. It also correctly distinguishes retrieval evidence from actual compliance. The compulsory “context receipt in the task transcript” introduces another agent-maintained record that can become noisy or inaccurate. Generate receipts from actual retrieval when possible rather than requiring the model to maintain a second account.

**Proposal E.** Concrete triggers and an explicit startup procedure improve first-reading comprehension without immediately changing parser semantics. Its separation of refreshing context from capturing findings is useful. But “compare every other visible description” still assigns exhaustive navigation bookkeeping to the model, while most eager catalogs and five reserved tag meanings survive. This is substantial editing with limited change to the underlying omission mechanism.

**Proposal F.** The drop-in directory is the strongest modular design because independent components can contribute required reading without editing a shared central list. It uses familiar files and existing entry syntax while allowing human documents to remain untouched. Treating a missing directory as no obligations must change before adoption. Reading every conditional source when paths are unknown also needs a bound, especially for conceptual tasks.

**Proposal G.** This is the strongest incremental candidate because fully tagged mandatory file branches address a concrete discovery failure using existing machinery. Optional catalogs and ordinary documentation roots provide useful savings without requiring wholesale semantic replacement. Its remaining burden is inherited applicability, ancestor recovery and semantic selection for task-based branches. Those costs remain even after the prose becomes friendlier.

**Proposal H.** It specifies the computed read set most precisely, including effective bodies, selection reasons, deduplication and incomplete results. Independent source conditions also make document reuse easier. Its manual fallback ignores available path filters and reads every required source, which can destroy the footprint benefit in a grown workspace. That shifts practical relevance scaling toward the CLI.

**Proposal J.** Its strongest contribution is the delivery split between immediate Markdown improvements and subsequent routing support. It is appropriately cautious about migration, write ownership and older tools. However, it retains nearly every consequential runtime mechanism, including hidden-parent discovery and semantic overwrite interpretation. Its startup target buys less simplification than proposals that remove those mechanisms.

#### Steal list

- **Proposal F — Independently owned required-reading drop-ins.** The final design should let a component add or remove its reading obligations without coordinating edits to one shared registry.
- **Proposal H — Verbatim context with paths and selection reasons.** Explainable retrieval provides inspectable evidence without pretending that retrieval proves compliance.
- **Proposal C — Separate reading conditions from source use.** Required reading must explicitly distinguish instructions, supporting knowledge and continuation state, even if the final representation avoids a new table grammar.
- **Proposal A — Validate customizations against their expected base.** Updates must expose stale assumptions in local replacements instead of silently carrying them forward.
- **Proposal J — Separate immediate reductions from routing implementation.** The maintainer should be able to obtain useful savings before committing to the complete replacement engine.

#### Most dangerous idea

Proposal F says, **“A missing or empty directory requires nothing.”**

That makes an incomplete checkout, damaged installation or accidental deletion indistinguishable from an intentional decision to remove every obligation. Required configuration needs an explicit empty representation. A missing declared inventory should produce an incomplete result before affected work proceeds.

This is a small clause with a large failure consequence.

#### Convergence

- Load the CLI Skill when it is needed.
- Move authoring and package-maintenance detail out of startup.
- Remove the inherited-empty marker requirement.
- Keep critical required context early.
- Use descriptions to select optional material before opening bodies.
- Let ordinary documentation participate at its existing path.
- Keep reading visibility separate from instruction authority and acceptance.
- Preserve native Skill activation and resource rules.
- Preserve existing records during migration.
- Judge actual reads and task behavior, rather than self-reported compliance.
- Treat concept counts and word savings as supporting evidence, not proof of reliability.

#### Open conflicts

1. **Explicit registrations versus metadata inventory versus inherited catalogs.**  
   C, D and F expose required registrations. H discovers required sources throughout registered folders. A, E, G and J retain selected catalog trees. I recommend F’s modular explicit registrations as the destination, with G’s tagged-chain checks as an incremental step. This gives components independent ownership and makes mandatory enrollment visible.

2. **Pending conditions versus conservative loading of everything.**  
   B, C, D, G and J preserve pending conditions. F and H read conditional material broadly when paths are unknown, with H also doing so throughout its manual fallback. I recommend reading unconditional instructions first, identifying candidate paths from filenames, then resolving conditions before body investigation or changes. File-less discussion should not automatically consume every language and subsystem policy.

3. **Semantic overlays versus checked patches versus complete replacements.**  
   Several proposals retain corresponding-content interpretation, A introduces checked patches, and H uses complete replacements. I recommend complete replacement sources with expected-base drift detection borrowed from A. Keep legacy overlays during transition, but avoid putting a sentence-patching language into the core loader.

#### Revised position

I would change five things.

- **Use modular registrations.** Replace the single required-rule registry with independently owned drop-ins, while keeping every mandatory dependency explicit and reporting missing declared configuration.
- **Distinguish required references from instructions.** Adopt C’s separation of reading and use, allowing an ordinary contract to be required reading without forcing it into an instruction-file shape.
- **Keep Memory organization available as an optional recipe.** Offer the existing state distinctions and ordinary project conventions, with exact active continuation records explicitly registered. A default empty checkpoint need not be compulsory.
- **Separate updater changes from loader delivery.** Follow J’s staging and evaluate the smaller startup independently of ownership reconciliation and replacement semantics.
- **Require explainable retrieval and behavioral evidence.** Use H’s source paths and matching reasons as the basis for D’s receipts, then test actual outcomes through the same fixtures with and without the CLI.

I would retain the short operating protocol, target-local applicability, direct participation by human documentation and the separation between required reading and optional discovery. The revised design should spend additional words only where they close a demonstrated ambiguity.

## Newcomer (Proposal G)

#### Critiques

**Proposal A**

Its strongest contribution is making local replacements checkable against expected source text, with an honest account of the limits of that check. Its serious weakness is expanding the design into replacement syntax, tag aliases, metadata fallback, and changed updater behavior while retaining parent-dependent mandatory discovery. I would retain override compatibility checks as an advanced capability and leave tag expansion out of the initial simplification.

**Proposal B**

Separating navigation from authority gives catalogues a clear purpose and makes direct documentation links straightforward. However, “follow the agent tool’s instruction precedence” does not specify where catalogue-selected rule files sit relative to native instructions. That relationship needs a portable default and compatibility evidence before removing the existing inheritance contract.

**Proposal C**

The `When`, `Read`, and `Use` columns make applicability and intended use visible together, and missing reading tables fail explicitly. The main weakness is introducing a new grammar while task rows still require semantic matching and the central table grows with the workspace. “Include plausible matches” could also load loosely related instructions, so ambiguous task matches need a clearer treatment.

**Proposal D**

Its strongest contribution is a directly inspectable required-reading checklist using existing Entries syntax. The compulsory “context receipt” adds bookkeeping whenever paths change, without establishing that the retrieved instructions were understood or followed. I would retain selection reasons and retrieval evidence, but make transcript receipts optional unless a particular workflow needs them.

**Proposal E**

Concrete action triggers and separating refresh from capture are useful improvements that can largely ship through Markdown changes. However, comparing every visible description still leaves required-context completeness dependent on repeated model judgment. It improves execution of the existing protocol more than it reduces its bookkeeping.

**Proposal F**

The drop-in directory offers the clearest story for independently installing, disabling, and removing loading components. Its biggest weakness is reading every conditional source when paths are unknown, then refreshing the entire required set at every named boundary. That could consume substantial context and return the applicability-sorting work to the model.

**Proposal H**

Computing required reads independently of navigation clearly separates bookkeeping from judgment, and emitting bodies with paths and selection reasons is valuable. Its manual fallback requires inspecting all registered Markdown metadata and reading all required bodies without filtering, making the CLI practically important in larger workspaces. Complete replacement companions also turn small customizations into maintained forks of defaults.

**Proposal I**

It provides the clearest small core, with concrete shipped files and a direct answer to what happens next. Its main weakness is the single shipped active checkpoint, which needs an explicit answer for independent workstreams and concurrent sessions. Removing overwrites and changing Update behavior are also substantial decisions that need not be bundled with the shorter reading protocol.

**Proposal J**

It has the strongest delivery separation between immediate Markdown reductions, read-only documentation routing, and later mutation support. Its serious limitation is preserving mandatory discovery through discretionary parent selection, so the shorter loader reduces explanation more than mechanical decisions. It is a strong first increment, but an incomplete answer to the rule-discovery problem.

#### Steal list

- **Proposal I: Direct registration of every mandatory rule source.** Required-rule discovery must not depend on selecting the right optional reference branch.
- **Proposal F: Independently removable read-list components.** A package should be able to contribute or remove its loading configuration without rewriting a shared policy document.
- **Proposal H: Verbatim context with paths, selection reasons, and explicit incomplete results.** Readers need to inspect what the mechanism selected and what remains unresolved.
- **Proposal A: Expected-text checks for local replacements.** Updates should expose stale customization assumptions rather than asking a model to infer compatibility.
- **Proposal J: Separate Markdown simplification from routing and lifecycle implementation.** Each behavioral change needs evidence without making the first improvement depend on completing the entire redesign.

#### Most dangerous idea

**Making complete replacement companions the default customization mechanism, as in Proposal H.**

A small local exception becomes a complete copy of a default, including its loading metadata. Future corrections and newly required instructions in the base can remain hidden behind that copy. Version-gating the initial migration does not prevent later divergence.

Complete replacements should remain an explicit fork with visible upstream differences. Reusing `.overwrite.md` for this behavior also increases the chance that users misunderstand what their existing customization now preserves.

#### Convergence

- The loader should teach a short operating procedure.
- Authoring and package maintenance details belong in focused references.
- The CLI Skill should stop loading merely because it exists.
- Critical instructions must be available before affected work.
- Descriptions remain useful for selecting optional context.
- Ordinary documentation should participate at its existing path.
- Routing participation must not grant installer ownership or write permission.
- Recording, tagging, and moving material do not establish acceptance.
- Memory organization should be removable and adaptable.
- Semantic changes require reviewed migration.
- Behavioral checks need actual reads and outcomes, not compliance claims or word counts alone.

#### Open conflicts

1. **Required discovery: selected hierarchical chains, explicit reading registrations, or a metadata inventory.**

   I recommend **explicit reading registrations**, potentially supplied through removable drop-ins. They give manual readers a finite checklist without requiring them to scan every document’s metadata. Keep nested catalogues for optional discovery. Test registry growth against a realistically large fixture before accepting the scaling tradeoff.

2. **Applicability ownership: source-local frontmatter or reading-list conditions.**

   I recommend **reading-list conditions for automatic retrieval**, with the source stating its actual scope in readable text. This lets existing human documents participate without acquiring framework metadata. Avoid maintaining two authoritative copies of the same loading condition. Frontmatter can remain useful for descriptions, search, and generation.

3. **Customization: semantic companions, checked replacements, or complete source substitution.**

   I recommend **checked replacements for precise exceptions**, with explicit whole-source substitution available when a user wants a fork. Keep advanced replacement syntax outside the startup lesson. Preserve existing companion semantics during migration rather than silently assigning the filename a different meaning.

#### Revised position

I would now separate mandatory reading from optional catalogues. The required set would be directly registered, with no discretionary ancestor between the starting procedure and a mandatory source. Optional knowledge could retain a nested catalogue structure.

I would allow registrations to point directly to existing documents without requiring entrypoints in every intermediate folder. The source would retain its own meaning wherever linked.

I would keep unknown file conditions pending rather than read every conditional policy. A compact unconditional baseline would support investigation until working paths become known. Continuity would identify the relevant workstream record, avoiding a universal shared checkpoint.

I would make required-reading membership authored policy that Index preserves. Computed output would explain selected, skipped, and unresolved entries. Receipts would be available for diagnosis without becoming routine transcript ceremony.

Finally, I would stage the work: shorten the current Markdown, evaluate an explicit required-reading registry, then implement native documentation routing. Override compatibility checks would be a separate capability. I would defer tag aliases, updater-policy changes, and wholesale Memory reorganization until evidence shows they are necessary.

## Unix Greybeard (Proposal F)

#### Critiques

**Proposal A.** Its strongest contribution is making replacements checkable against named source text, turning an inferred merge into an inspectable operation. However, the loading design retains discretionary parent selection, ancestor recovery and inherited conditions, so its principal discovery failure remains. Tag aliases, a replacement language and changed updater behavior also enlarge the implementation well beyond the short loader.

**Proposal B.** Separating navigation from inherited instructions makes directly linked documentation substantially easier to adopt independently. Requiring an uninterrupted discovery chain for mandatory file rules is also a useful safeguard. Its weakest boundary is “follow the agent tool’s instruction precedence,” which does not clearly explain how conflicting rules in ordinary project documents compose across different hosts.

**Proposal C.** The reading table gives people one place to inspect applicability, destinations and intended use, including conceptual tasks without known files. It also distinguishes temporary state from ordinary references without refreshing everything. Its serious cost is introducing a new grammar with three condition forms and three uses, while `task:` matching still depends on judgment and “include plausible matches” can produce substantial overreading.

**Proposal D.** Direct registrations with complete conditions address the hidden-parent problem using mostly existing syntax, and the proposal carefully distinguishes its tabletop traces from behavioral evidence. It also treats required lists as authored policy rather than directory-generated inventory. The mandatory context receipt adds recurring transcript bookkeeping and can become the agent certifying its own account, so it should be computed evidence or optional diagnostic output.

**Proposal E.** Concrete triggers and an explicit selection procedure improve the chance that readers execute instructions rather than merely remember definitions. The conservative migration is credible. However, comparing every visible description still leaves mandatory discovery dependent on relevance judgments, while eager catalogues, inherited conditions and a universal Templates check retain considerable startup ceremony.

**Proposal G.** This is the strongest conservative compromise, with optional advice catalogues, a smaller Memory baseline and explicit required chains for file-specific rules. It preserves much of the existing parser and manual procedure. Its weakness is that reliability now depends on authors correctly tagging every parent, while conceptual branches still require selection and directly reached files still need their ancestry reconstructed.

**Proposal H.** Computing required reads independently of navigation directly addresses missed parents, and its proposed CLI output is unusually concrete about paths, reasons and effective bodies. Keeping human documents at their original paths is also well handled. The manual fallback requires inspecting frontmatter throughout registered trees and reading every required source without filtering, which can make the CLI practically necessary in a large workspace despite remaining formally optional.

**Proposal I.** It specifies the whole small startup payload rather than presenting a short loader surrounded by unchanged machinery. The direct rule list, source-local conditions and explicit replacement destinations are understandable and compose well. Its weakest default is the single compulsory active checkpoint, which needs a clear policy for unrelated work and concurrent tasks, while changed updater behavior adds another substantial delivery boundary.

**Proposal J.** Its strongest contribution is the delivery sequence, separating immediate Markdown reduction from read-only documentation routing and later mutation support. That makes cost and compatibility easier to control. The resulting loader nevertheless preserves most of the current operating model, including parent-gated discovery, ancestor recovery, inherited predicates and semantic overwrites, so much of the conceptual burden survives.

#### Most dangerous idea

Proposal B’s suggestion that Open Forge should “follow the host’s precedence rather than introduce another hierarchy” is dangerous if extended to composition between ordinary project sources.

Native platform instructions must remain respected. However, a broad engineering requirement and a local exception in `docs/` should not acquire different meanings merely because another agent runtime reads them. Keep a common rule for project-source conflicts, with explicit replacement or declared authority and visible unresolved disagreement.

- Remove the compulsory CLI tutorial from startup.
- Move installation and authoring detail out of ordinary task reading.
- Stop requiring inherited markers.
- Let existing documentation participate at its original path.
- Keep Maps useful without making them compulsory adapters.
- Preserve acceptance as distinct from evidence, confidence, tags and file placement.
- Make required reading explicit before affected work.
- Keep optional capabilities and content removable.
- Measure actual behavior rather than treating fewer words as proof.
- Migrate inherited conditions and local customizations through reviewed changes.

The proposed concept counts use different units. They should not decide the outcome.

#### Open conflicts

1. **Mandatory discovery: explicit lists, metadata inventory or recursive selection.**  
   D and I use direct registrations, H inventories registered folders, and A, E, G and J retain recursive selection. I recommend explicit lists using the existing Entries syntax. They expose membership, admit unchanged human documents and avoid scanning entire documentation trees. Test their growth against a realistically large workspace before committing.

2. **Customization: semantic overlays, checked patches or complete replacement.**  
   B, D, E, G and J retain corresponding-content overlays, A introduces checked patches, and C and I use replacement destinations while H uses complete replacement companions. I recommend explicit replacement destinations as the base mechanism. Offer checked patches as optional tooling only after demand justifies their parser and maintenance cost.

3. **Manual fallback: matching procedure or conservative superset.**  
   D and I retain conditions and pending paths without the CLI, while H reads the entire required set. I recommend the same matching contract with either tool path. Read unconditional context immediately, identify working paths, then resolve conditions before affected investigation or edits. This preserves context economy without making a successful command responsible for defining applicability.

#### Revised position

I would keep drop-in assembly and direct links to independently usable documents, with four changes.

First, I would adopt pending file conditions when paths are unknown. Unconditional rules should load immediately, while conditioned sources must resolve before their governed work.

Second, I would stop rereading the entire required set at every closeout. Start, resume, restoration and path expansion need required-context checks. Closeout needs the active continuation state and sources that may have changed. A narrowly applied continuity marker is worth retaining if it expresses that distinction clearly.

Third, I would separate the loading experiment from updater reform. Preserve existing lifecycle behavior until a separately reviewed change establishes how editable configuration survives updates.

Finally, I would specify the complete shipped startup pack and use D’s inspectable required set and H’s explained retrieval output as evaluation artifacts. Any receipt should come from observable reads where possible, without requiring repeated prose declarations from the agent.

## Steward (Proposal J)

#### Critiques

**Proposal A.** Checked replacements give customization an inspectable failure boundary, especially when upstream text changes. Its serious flaw is bundling several redesigns into simplification: replacement syntax, tag aliases, metadata fallback, update reconciliation, and broader routing. These are individually plausible, but collectively add substantial machinery while leaving mandatory branch discovery dependent on selection.

**Proposal B.** Separating navigation from instructions makes catalogs easier to understand and ordinary documentation easier to adopt. However, “Follow the agent tool’s instruction precedence” delegates an important contract without specifying how catalogued rule files participate in that hierarchy. Host-specific adapters could resolve this, but the proposal removes portable semantics before supplying their replacement.

**Proposal C.** The distinction between required `instructions`, `reference`, and `state` reads is excellent because mandatory reading need not make a document behavioral policy. Its main weakness is replacing the existing protocol with another language, including `always`, `files:`, `task:`, and three use modes. “Include plausible matches” also leaves potentially expensive semantic selection across a global table, so improved discovery does not automatically mean smaller working context.

**Proposal D.** This offers the strongest diagnosis of mandatory discovery failures and a concrete fixture that can expose them. It correctly distinguishes tabletop counterexamples from measured model behavior. Its serious weakness is transferring completeness to an authored registry whose missing registrations remain difficult to detect, while flattening inherited conditions requires substantial migration. A context receipt helps inspection but cannot establish that the registry was complete or the reported reading occurred.

**Proposal E.** Its strongest contribution is an executable work loop with instructions placed at the moment they matter, while preserving existing syntax and treating blending as substantial engineering. This provides a credible reduction without making tooling essential. Its main limitation is that “every selected index has been checked” cannot establish that an important unselected branch was discovered. More systematic description matching remains model judgment rather than mechanical completeness.

**Proposal F.** Drop-in read lists offer the clearest independently removable registration mechanism, using familiar filesystem operations. However, “A missing or empty directory requires nothing” makes an accidentally missing required directory indistinguishable from intentional absence. Reading every conditional source when paths are unknown, then refreshing all required context at closeout, can also erase the promised savings in grown workspaces.

**Proposal G.** Requiring a fully tagged discovery chain for mandatory file-specific rules is a valuable improvement using existing loading mechanisms. Its everyday language, optional capabilities, and explicit documentation enrollment form a coherent design. The main weakness is authoring responsibility: complete chains and compatible conditions must stay correct as files move. Proposed structural checks need precise boundaries so they distinguish an intentionally optional scope from an accidentally hidden mandatory branch.

**Proposal H.** Computing required context from current metadata and working paths cleanly separates mechanical retrieval from semantic judgment. Verbatim bodies with paths and selection reasons also preserve inspectability. Its largest weakness is the manual fallback, which scans registered metadata and reads every required body even when working paths are known. That may preserve availability while making ordinary use impractical at precisely the workspace sizes Open Forge intends to support.

**Proposal I.** This supplies the most complete demonstration of a genuinely small default installation, rather than only a short loader. It also states capability losses unusually clearly. Its serious flaw is coupling the required-list design to deleting overlays, changing Update behavior, removing inherited scope, and replacing Memory with one active checkpoint. That checkpoint needs a clear extension for simultaneous workstreams, otherwise unrelated work can overwrite or mix continuation state.

Requiring the agent to update a transcript receipt whenever another path appears introduces new bookkeeping, while the receipt itself cannot prove reading or compliance. Selection receipts should come from tool output, with behavioral claims checked against actual traces.

**Proposal E**

Concrete action triggers and a conservative migration make this a useful candidate for an immediate prose experiment. However, “Compare every other visible description” turns discovery into a longer checklist while retaining inherited conditions, parent activation, refresh tags, and semantic overwrites. It reduces explanation substantially without moving enough operational work away from the model.

**Proposal F**

The drop-in directory gives required reading a predictable entry point while preserving modular configuration and direct links to human documentation. Its most serious flaw is treating a missing directory as equivalent to intentionally empty policy. Refreshing the complete required set at every boundary also needs measurement against realistic workspaces rather than only small fixtures.

**Proposal G**

Requiring a fully tagged parent chain for file-specific rules is the strongest incremental repair among proposals retaining the existing hierarchy. Everyday Memory display names also improve comprehension without forcing record moves. However, sources still depend on ancestor catalogs for instruction context, and keeping every parent correctly tagged remains an authoring obligation that needs concrete validation.

**Proposal I**

I supplies a complete default startup set, making its footprint claim more inspectable than a loader-only budget. Its flat rule list and source-local conditions provide a particularly clear operating protocol. The compulsory shared `memory/checkpoint.md` lacks the workstream identity and retirement boundary present in the current Checkpoint contract, creating avoidable risks during concurrent or alternating tasks. Checkpoint organization and changed Update behavior should be evaluated separately from the reading protocol.

**Proposal J**

J has the strongest delivery discipline, separating an immediate Markdown reduction from read-only blending and later mutation support. Its final protocol nevertheless retains recursive selection, ancestor recovery, inherited matching, two instruction containers, and refresh bookkeeping. It is a credible first release slice, but a weaker endpoint for the maintainer’s concern about model-dependent procedures.

#### Steal list

- **Proposal F: separate required reading through drop-in manifests.** This provides a small, composable registration surface that people and agents can inspect without traversing optional knowledge catalogs.
- **Proposal C: distinguish empty policy from missing policy.** The final design must permit intentionally empty configuration while reporting unavailable or invalid required-reading configuration.
- **Proposal H: emit verbatim source bodies with paths and selection reasons.** Computed context must remain inspectable against the files that define its meaning.
- **Proposal I: account for the complete default startup set.** Footprint claims must include required catalogs, notes, metadata, and bridges instead of stopping at the loader’s word count.
- **Proposal J: stage prose, read-only blending, and lifecycle changes separately.** Each behavior change needs an independently reviewable experiment and migration boundary.

#### Most dangerous idea

Proposal F’s statement that “A missing or empty directory requires nothing” is the most dangerous individual rule.

Once a workspace adopts required-list loading, an accidental deletion, incomplete checkout, or unavailable configuration must not produce an apparently successful zero-rule startup. Empty authored policy and missing policy require different outcomes. Require an existing bootstrap manifest, which may validly contain no entries, and report missing or invalid configuration as unresolved context.

This is a small correction to F’s architecture, but essential to its reliability claim.

#### Convergence

- Remove the compulsory startup read of the CLI Skill.
- Move authoring and package-maintenance detail out of ordinary startup.
- Retire the inherited marker requirement.
- Let ordinary documentation participate at its existing path.
- Preserve the distinction between pointers and destination knowledge.
- Keep acceptance separate from confidence, evidence, tags, and file movement.
- Make Memory organization optional and preserve useful continuation state.
- Keep native Skills under their runtime’s rules.
- Keep the files understandable without the CLI.
- Evaluate actual reads and resulting behavior, not declarations of compliance.

Concept counts themselves do not converge. Different proposals count different units, so they should not be used as comparative scores.

#### Open conflicts

1. **Mandatory discovery: explicit required lists or tagged catalog chains.**  
   C, D, F, and I make mandatory enrollment directly inspectable. A, E, G, and J retain hierarchical discovery, with different safeguards. I recommend explicit lists using F’s drop-in organization and the existing Entries syntax. Optional knowledge can retain hierarchical catalogs. This removes mandatory ancestor selection without introducing C’s additional table language.

2. **Condition ownership: source frontmatter or authored reading links.**  
   A, B, G, and J retain source metadata as the condition surface. C, D, F, and I place required-reading policy in a registration surface, although I also mirrors destination metadata. I recommend authored link conditions as the single loading authority. A human document should not need Open Forge metadata merely because one workspace requires it for certain tasks. Frontmatter can provide generation suggestions, but must not silently create a second policy.

3. **Customization: semantic overlays, checked patches, or complete source substitution.**  
   B, E, G, and J retain interpretation of corresponding content. A defines checked patches. C, F, and I prefer explicit source replacement. I recommend source substitution for the new minimal format. Preserve legacy companions until reviewed migration. Introduce checked patches only if real customization cases justify their additional grammar, with no automatic conversion of ambiguous prose.

#### Revised position

I would revise my proposal as follows:

- Adopt **F’s explicit drop-in manifests** as the primary mandatory-reading surface. Participating human documents would not require loading tags in their own frontmatter.
- Put complete conditions on authored registration links, following **D and F**, with no inherited conditions and no independently active metadata policy.
- Adopt **C’s missing-versus-empty distinction** for the bootstrap configuration.
- Prefer explicit replacement links for new workspaces. Retain existing overwrite semantics during transition rather than changing the meaning of an existing filename immediately.
- Test **D and I’s pending-condition approach** against conservative reading when paths are unknown. I would no longer assume that reading a superset is necessarily safer, since incorrectly applying conditional instructions is also a failure.
- Keep continuation records per workstream, with explicit identity and retirement. Avoid a compulsory global checkpoint.
- Retain verbatim CLI output and selection reasons. Any context receipt should be derived from that output rather than maintained independently by the agent.
- Follow **J’s staged delivery**. Trial the shorter prose under existing semantics first, compare explicit-list fixtures separately, and implement the new reader once manual and computed source sets agree.

The initial implementation should focus on retrieval. Memory taxonomy, Update reconciliation, custom tag aliases, and patch languages should remain separate decisions.
