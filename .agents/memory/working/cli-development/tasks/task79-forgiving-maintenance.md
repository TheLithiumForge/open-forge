# Task 79: Forgiving maintenance after manual edits

## Outcome

A user can rename, move and create Markdown files by hand, without the CLI and without frontmatter, and Open Forge still works. `index`, `doctor` and `repair` notice what changed, fix navigation, fill in what is missing with sensible prefilled values, repair links to files they can prove were renamed or moved, and tell the user the one next command when something still needs attention. The CLI is forgiving and helpful rather than strict.

The maintainer asked on 2026-10-13:

> "As a user, I have a bunch of files in some scopes or whatever, doesn't matter. I want to, like, let's say I am too lazy to just spin up another agent or whatever. I just want to rename the file manually. I don't even want to use the CLI. Then the CLI should be able to later on, I don't know, via doctor repair or something else, fix the broken links, and the indexing should still totally work normally wherever I renamed it or moved it, because, and that would mean basically removing the old entry and updating to the new entry."

> "Another one that should also work is I create a normal file, no front matter, no nothing. I should be able to index that, and the front matter should be auto-generatable."

> "I should be able to deeply nest some file. Like I'm gonna create a few scopes, no entry point for the scopes, and then just put like a node.md or whatever in that last scope, even without the front matter. That means the CLI on index, I think, should create the entire tree of entries and put the front matter in all of them."

> "The CLI should be very, very forgiving and helpful rather than strict and throwing errors or whatnot. Like the user, even if the user is an absolute doofus, it should still work."

They asked for user flows, scenarios, documents and end-to-end tests that prove these journeys.

## Current behavior (beta.12 plus Task 78, reproduced 2026-10-13)

- **Manual rename.** `index` replaces the old entry with the new one correctly. `doctor` reports the broken authored link and suggests `open-forge repair`. `repair --automatic --dry-run` says `Nothing could be repaired automatically. 1 problem needs a choice.` with three possible targets and suggests the same command again. If `index` runs first, the stale entry that described the old file is gone.
- **Plain file without frontmatter.** `index` lists it with its source ID as the label (`guidance/deploy-checklist`) and warns `Optional metadata is missing`. `doctor` then says `Required route metadata is missing.` and `Fix it by hand.`, which contradicts index.
- **Deep nesting.** With `memory/crystallized/platform/payments/stripe/node.md` and no entrypoints, `index` says `Entries sections are current in all 12 files. Nothing to do.` `doctor` says the file `is routed but no parent lists it` and suggests `open-forge index`, which does nothing. The user has no working next step.

## Accepted decisions

- **D1 Index fills missing frontmatter (maintainer, 2026-10-13).** When `index` finds a routed Markdown file without frontmatter, or with some fields missing, it writes prefilled metadata in the workspace's metadata form: a description from the first heading, or from the file name when there is no heading, and tags from the folder's category. Only missing fields are added. The body and existing fields stay exactly as authored. `--dry-run` shows it, and the result says `metadata completed, your content was kept`. This supersedes flow F03's expectation that index never edits a plain note.
- **D2 Index completes missing entrypoints.** When routed Markdown sits in folders under a recognized root route that have no entrypoints, `index` creates the missing entrypoints for the whole chain, with prefilled frontmatter and the inherited-axioms marker, and lists every new entry. This follows from the maintainer's request and from F05's existing target of creating missing intermediate scopes without a ritual.
- **D3 Proven renames and moves are repaired without asking.** A link to a missing file is repaired automatically when there is exactly one candidate with strong evidence that it is the same file after a rename or move. Strong evidence means Git sees the old tracked path removed and the candidate with the same or nearly the same content, or the candidate's content or metadata matches what the old file or its stale entry recorded. A filename or title guess alone stays a choice for the user, as F08 already requires.
- **D4 One next step.** After manual edits, `doctor` names the problem in the user's terms (for example that a file looks renamed) and gives one command that fixes everything safe. Every command's result says what to run next when something remains, and running those commands in order reaches a clean `doctor`.
- **D5 Base.** Task 79 branches from `feature/task78-clear-docs-and-wizards` at `28c32aee7` as `feature/task79-forgiving-maintenance` (maintainer, 2026-10-13). Task 78 stays unmerged until the maintainer decides.

## DS1 investigation and reproduction

DS1's inspected implementation boundaries are recorded below. The [current shared capabilities](../../../crystallized/documents/cli/technical-designs/forgiving-maintenance.md#shared-capabilities) describe the integrated realization. The pre-implementation failures came from these separate boundaries:

- Index forms its selected closure from existing entrypoints, then plans only generated-region replacements. It never scaffolds a gap or inserts ordinary metadata. Missing metadata retains observed description and tags, otherwise the automatic source ID becomes the Entries label.
- Doctor observes a broader source and route-shape inventory. It marks Missing ordinary metadata as required with a manual lane, while its output recommends Index for unreachable files regardless of whether the current Index closure can reach them.
- Repair builds candidates from a matching filename, first level-1 title, matching link or heading label and structural neighborhood. A missing target always becomes a guided proposal. Automatic selection requires an existing exact resolution, so neither unchanged content nor a Git rename can currently prove that candidate.
- Route Init already composes a canonical chain, workspace-form metadata, the inherited marker and prospective generated navigation. Generic defaults are `Draft route for <id>; replace this description before relying on it for selection` and `[NeedsAuthoring]`. Framework restoration alone may clear the exact selected exclusion. A plain note can still prevent its strict metadata projection from completing the chain.
- Update's `metadata completed, your content was kept` path currently completes native Skill name/description through parser-span insertion. The ordinary document planner validates metadata and may append Entries, but does not insert ordinary description/tags. Both root and scoped emitters and bounded form transformation are reusable mechanics, not proof that Update already completes plain ordinary notes.
- GitProcessRunner executes read-only argument lists, disables optional locks and fsmonitor, clears ambient repository selectors, suppresses prompts, and kills/drains cancelled children. Git-ignored enumeration is already NUL-delimited and deadline-bounded. Git absence produces unavailable optional observations rather than a substitute workspace. Index's privacy policy comes from the ownership lock, not general Gitignore enumeration.

## Design decisions (Overseer, 2026-10-13)

The Overseer accepted the DS1 design and settled its three open questions within the maintainer's direction that the CLI forgive manual edits, then decided items 5 to 9 during implementation and review. The technical design records each one.

1. **Folder renames keep their navigation file.** When rename evidence proves a folder's old canonical entrypoint moved with it, Index renames it to the new canonical name, keeping its description, Axioms and body exact. The folder keeps the rules it had before the rename. Without proof, Index scaffolds a new entrypoint and Doctor explains how to keep or remove the old file.
2. **Near-identical content.** Keep the deterministic 90% weighted-line threshold and the unique-candidate rule.
3. **Partial headers in the other form.** Complete the missing fields in the header's existing declaration form, keeping supplied bytes exact. New headers and entrypoints use the workspace form.
4. **Files outside routed folders.** Doctor explains that the file is outside the routed folders and how to move it or add its folder to the Loader. Index does not invent a root.
5. **Index before Repair keeps the proof.** R2 found that the successor's new generated row blocked a Git-proven relink after Index. A current generated row is not a prior identity. Only a committed identity at the successor path contradicts committed-content or near-identical proof, and a metadata-only proof keeps the stricter rule. Both command orders must repair a proven rename.
6. **Doctor explains, then acts, and never points to itself.** Each finding says what is wrong and what to do without repeating a sentence. A missing Entries target is reported once. A clean Doctor prints no Next, and an incomplete one says it could not finish.
7. **Repair never leaves a choice without a way to make it.** When Repair cannot ask, each guided link lists its candidates with the exact relink command, in human text and in JSON finding actions. A listed choice comes before Index, and a chosen relink refreshes the affected navigation once no other broken link still needs the old identity.
8. **A Git timeout proves nothing.** Repair and Doctor admit no rename proof while Git has timed out, say so, and repeat the request. Absent Git keeps the stale-metadata fallback.
9. **Protected sources stay untouched.** Repair applies the shared protection rules to every link source and target, and Doctor promises only what Repair will do.
