# Generic Extension Content Review

## Scope And Direction

Baseline: `d2e2e33fead58f55348ce307087e9492c12514e1`. The user asked for generic, helpful Extension content that leaves room for project facts and inherits applicable project rules. They also requested a separate assessment of Experience Design and questioned excessive package fragmentation.

The source author inspected all nineteen non-Skill package content files and the two affected READMEs, then prepared five new planning files. The primary owner reviewed the complete source diff and retained content, assessed all four Experience Design files separately, and reviewed the local alignment. This was content review and static verification, not a measured agent-performance experiment.

## Applied Content

- All seven Workflows now obtain concrete choices from the project's applicable scopes and current sources. Development retains flexible test ordering; Debugging identifies the source of expected behavior; Review retains exact target identity, finding IDs, false-positive checks, and read-only boundaries. Vision and Architecture use existing defining sources without requiring a separate document every time.
- Managed Delivery retains every task's identifiable baseline and working-location check. A precise starting state is valid when revision control does not apply. Git revisions remain the baseline where applicable. Parallel isolation, authority, preservation, and discrepancy checks remain intact.
- Work Records supplies default separate-record shapes and explicit relationships with existing task systems. A small task can remain one record. Each mutable fact has one defining source.
- The [Planning Templates](../../../../../src/extensions/planning/content/.agents/templates/planning/_planning.md) add Task, Plan, Backlog, and Checkpoint starters under one on-demand scope. Removable prompts leave the actual project content to the user. The Checkpoint starter links to the installed destination rules for active continuity and closeout.
- Vision no longer assumes that existing approaches are inadequate or that every project maintains repeated entry summaries. Architecture links to required behavior's defining sources. Maintenance supports appropriate verification without assuming a runtime or existing automation.
- The package READMEs describe the actual thirteen Templates and their relationship with project context.

The two existing Template entrypoints, Principles Template, and five Memory Templates were retained after inspection. Their selection, removable prompts, authority, and lifecycle boundaries already fit the requested generality.

## Local Alignment

The three changed document Templates and Work Records Pattern match their package sources. The four new planning starters and their entrypoint have matching local copies and a generated route entry. Repository-specific Workflow profiles and existing specialized Task/Plan Templates are preserved.

The accepted authoring boundary is recorded in the Framework change instructions and the [Extension architecture](../../../crystallized/documents/extensions/architecture.md#reusable-content-and-project-context). The [catalogue synchronization task](../../cli-development/tasks/extension-catalogue-synchronization.md#planning-starter-follow-up) records the additional checks for the separate CLI implementer.

## Verification And Limits

Static verification checks exact source application, package dependency closures and destination conflicts, runtime Markdown links, generated entry descriptions and tags, recipe section order, Template metadata and removable instructions, local parity, and changed documentation links. Reasoned traces cover a small task kept in one record, a separately maintained plan, an external task source with local resumption context, an inconclusive debugging investigation, a read-only review, and interrupted work without Git.

Existing source tags, the base Framework, package manifests, and the Experience Design Skill are unchanged. No CLI implementation, contracts, tests, build, execution, package installation, or runtime qualification is included. Package redistribution and the Skill removal decision remain separate from these completed content improvements.

[Task 28](../../cli-development/tasks/source-framework-review.md) defines current progress. The [package proposal](../../../emerging/analysis/framework-review/extension-package-proposal.md) and [Experience Design assessment](../../../emerging/analysis/framework-review/experience-design-value.md) remain candidate distribution analysis.
