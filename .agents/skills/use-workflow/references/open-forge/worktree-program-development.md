# Managed Worktree Project Development

## Goal

Deliver an explicitly requested parallel project wave without making the user coordinate task owners, sessions, worktrees, branches, integration, or review.

When integration or acceptance remains pending, prepare a reviewable handoff and identify the unfinished delivery boundary.

Use direct or sequential execution when parallel work was not requested, the work shares one semantic owner, or safe isolated child sessions are unavailable.

## Steps

1. **Reconcile the request.** Compare the requested outcomes with accepted vision, architecture, active work, dependencies, and baseline. Create or extend one project ledger only when the wave needs durable coordination.
2. **Confirm parallel authority.** Verify that the user requested parallel execution or already authorized this managed wave. Keep unresolved proposals separate from accepted decisions.
3. **Freeze the shared horizon.** Record only the architecture, ownership, contracts, safety and compatibility invariants, protected surfaces, evidence, and integration policy required by the wave.
4. **Choose independent lanes.** Default to two active mutating tasks. Use up to four only when semantic ownership and mutable paths are non-overlapping and integration remains bounded.
5. **Provision isolation.** Create each task from the exact accepted base commit in a distinct branch, worktree, and worktree-rooted session. Verify identity before mutation.
6. **Dispatch compact packets.** Give each Task Mastermind one outcome, execution profile, accepted contracts, owned capability, expected and protected paths, integration neighborhood, dependencies, evidence ladder, maximum review, council, and correction budgets, integration contract, and escalation conditions. Keep the profile, budgets, and consumed IDs in Markdown rather than frontmatter.
7. **Preserve implementation continuity.** Keep one implementation owner through tests, production, repair, local refactor, and focused verification unless an assured boundary requires independent ownership.
8. **Monitor durable state.** Track task checkpoint, Git identity, blockers, change requests, authorizations, and next milestone without copying complete transcripts.
9. **Resolve project discoveries once.** A task returns a project change request before changing shared meaning or another lane's assumptions. Resolve it once and invalidate only affected packets.
10. **Complete tasks locally.** Require canonical execution receipts and compact completion packets. When local commits are authorized, return clean task worktrees and coherent commits containing every relevant formerly untracked artifact. When committing is not authorized, retain the changed and untracked files in their task worktrees and record the base revisions, paths, and verification state. Tasks do not push or integrate themselves.
11. **Review task inputs when selected.** Use the ordinary review path by default. For uncommitted output, record the base revision and actual changed and untracked target, and revalidate findings if that target changes. An explicitly budgeted coordinated pass requires authorized task commits. If they are unavailable, leave that review pending and report the missing prerequisite. When they are available, give one read-only Review Mastermind a bounded list of independently owned snapshot records across exact task commits from several worktrees. Each record retains its semantic owner, display and lane, original return writer, lineage, changed and formerly untracked paths, contracts, protected paths, non-goals, receipts, and topic units, prefixes, and routing. The coordinator validates each record independently, preserves its actual ancestor, candidate, candidate parent, and separate authority commits and trees, validates ancestry, keeps at most one wave per task snapshot, and joins returns by snapshot and writer. It never treats a branch or worktree as the reviewed snapshot or gives one Task Mastermind authority over peer semantics.
12. **Check the integration boundary.** Proceed with steps 13–16 only when integration at the accepted target is authorized, required task acceptance and review are satisfied, and the input commits are available. Otherwise preserve the task worktrees and reviewable results, record the remaining decisions or prerequisites, and continue at step 17. For authorized integration, combine completed task commits in dependency order through the Integration Mastermind or a small direct integration. The Integration Mastermind does not own review topics.
13. **Reach green mechanically.** Resolve textual and direct conflicts while preserving accepted behavior and traceability. Reproduce focused evidence after each input.
14. **Converge semantically.** After green, generalize proven identical meaning, share neutral mechanism where policy differs, and leave coincidental similarity local.
15. **Gate proportionately.** Run affected integration, public, generated-output, compatibility, and full evidence appropriate to risk. Use independent review only for a named risk, followed by one grouped repair pass. When a required check or review remains unresolved, preserve the candidate, record what remains, and continue at step 17.
16. **Advance the baseline.** Do this only after authorized integration, passing required checks, and acceptance. If acceptance remains pending, preserve the candidate and continue at step 17. Preserve unfinished or unaccepted worktrees and records during interruption, recovery, or cleanup. Record the accepted commit, update affected project authority, retire internal resources safely, and start newly unblocked work from the new baseline.
17. **Report one result.** State whether the result is integrated delivery or a reviewable handoff. Report completed outcomes, decisive evidence, material residual risk, remaining checks or decisions, and the next meaningful action without exposing routine orchestration ceremony.

## Completion

For either outcome:

- one accepted baseline and any task results awaiting integration are identified;
- proposals and accepted decisions remain distinct;
- every task has one bounded owner and reviewable evidence;
- every parallel mutation used a real isolated worktree-rooted session;
- shared architecture was frozen before dependent work;
- review and full-gate cost matched named risks; and
- the user received one project-level result rather than an internal execution tree.

For integrated delivery, mechanical integration reached green before convergence, required checks and review passed, and the result was accepted before the baseline advanced.

For a reviewable handoff, preserve the task worktrees and any integration candidate. Identify exact commits or base revisions with changed and untracked paths, evidence already obtained, pending checks, and remaining integration or acceptance decisions. Keep delivery incomplete at that boundary.
