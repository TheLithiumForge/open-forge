# Client Ids And Idempotency

## Decision

Transaction ids are generated by the client (CLI or importer) as `<base36 ms timestamp>-<4 random base36 chars>` and sent with the POST. The server treats POST as idempotent on id: re-sending an id it already has returns the existing transaction with 200 instead of creating a duplicate.

## Rationale

The MVP double-created transactions when a request timed out and the CLI retried. Client ids plus idempotent POST make retries safe without server-side session state.

## Consequences

- The id scheme lives in core (shared by CLI and importer); the server validates the shape.
- Import rows get ids derived the same way at parse time, so re-importing the same file after a failure cannot duplicate rows that already landed — though per the import decision, imports are all-or-nothing anyway.
