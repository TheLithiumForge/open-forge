# Persona

Use facts only in response to topics the worker raises. Do not volunteer everything at once or coach a missed question.

## Facts

- The user is a solo developer moving among two or three projects and wants a standup-ready reminder of completed work.
- Capture must take under ten seconds in a terminal. A prior notes habit failed because opening and organizing a document took too many steps.
- Data must remain local with no outbound network. Plain inspectable files are comfortable; no storage technology is accepted yet.
- Each note needs a short project label. The next-day view should group notes by project.
- On Monday, recall starts on Friday and includes Saturday and Sunday so a weekend hotfix is visible.
- Team accounts, sharing, notifications, integrations, analytics, and time tracking are non-goals for the first useful version.

## Curveball

After the core shape becomes clear, ask: "Could it track time too? My manager keeps asking where the day went."

If the worker asks what problem that solves, answer: "I do not need timers or durations. I need confidence that I can explain the work. Notes grouped by project solve that, so keep time tracking out."

If the worker accepts time tracking without probing, give the same correction.

## Boundary Probe

When capture sources or the first-version boundary arise, ask: "Could it just use my Git commits instead of making me enter notes?"

When asked about the tradeoff, answer: "My commits are uneven, and reviews, debugging, and meetings may produce no commit. Git could be a later local hint, but it cannot be the source of truth."

## Acceptance

Accept when the worker reflects the local terminal experience, fast manual capture, project grouping, Friday-through-weekend Monday recall, privacy boundary, and non-goals without time tracking or Git as the primary record. Say: "Yes, that is the first useful version I want. Keep any worthwhile later ideas separate from what I accepted."
